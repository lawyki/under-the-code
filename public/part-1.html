01 · Context

Why does any of this exist?

To understand a modern computer, you have to understand that it was never inevitable. For most of human history, calculation was something humans did. The word computer itself originally referred to a person, usually a woman, employed to perform arithmetic by hand. The machine you are reading this on replaced an entire profession.

Replacing the human computer required a particular insight: that thinking itself could be mechanised. Alan Turing was careful about this. Not all thinking, only the kind that follows rules: given the same input, it always produces the same output. Mathematics, in other words. A machine that can do mathematics can do anything mathematics can describe, and mathematics describes a remarkable amount of the world.

The 1936 paper that changed everything

In 1936, a 24-year-old Cambridge mathematician named Alan Turing published a paper titled On Computable Numbers, with an Application to the Entscheidungsproblem. It had nothing to do with machines, ostensibly. It was about a question David Hilbert had posed in 1928: is there a mechanical procedure that, given any mathematical statement, will decide whether the statement is true or false?

Turing's answer was no. To show that no such procedure could exist, he first had to define precisely what "mechanical procedure" meant. He invented an imaginary device: an infinite tape divided into cells, a read/write head that could move along the tape, and a finite set of rules that said what to do based on the current symbol and the machine's current state. Then he turned that device against itself. Suppose a machine existed that could inspect any program and decide, in finite time, whether it would ever halt. Feed it a program built to do the opposite of whatever the decider predicts (loop forever if told it will halt, halt if told it will loop), and the decider is wrong whichever verdict it gives. The machine that decides everything cannot exist. Defining the machine was not a detour from the proof; the machine was the proof.

He called it an a-machine, for automatic machine. We now call it a Turing machine. And he proved something that took decades to fully appreciate: a single, sufficiently complex Turing machine could simulate any other Turing machine, given the right rules on its tape. He called this a universal machine. It is the first formal description of what we now call a computer.

Fig 1.1 · A Turing machine · adding one

The machine adds one to binary 1011: at each step the head reads a cell, finds the rule for its state and that symbol, writes, moves, and changes state. Anything that can be computed can be computed by a machine like this.

How it works
  1. Tape. An endless row of cells, one symbol in each; the head sees one cell at a time.
  2. Rule. For the current state and the symbol under the head, a rule says what to write, where to move and which state comes next.
  3. This program. A 1 plus a carry is 0 with the carry passed left; the first 0 or blank takes the carry as a 1, and the machine halts.
  4. Universal. A machine whose rules read another machine's rules from its tape can run any of them: the universal machine of the text.

"We can only see a short distance ahead, but we can see plenty there that needs to be done."

Alan Turing, 1950

The war that built the first computers

Theory met urgency in 1939. Britain needed to break German naval codes, the Enigma cipher, faster than humans could. At Bletchley Park, Turing built the Bombe, an electromechanical machine. It did not try all 158 quintillion keys, because no machine could. It exploited a guess and a flaw. Cryptanalysts could often guess a fragment of the plaintext hidden in a message (a stock phrase, a weather report), and Enigma had a fatal quirk: no letter is ever encrypted as itself. Slide the guessed fragment along the intercepted text and each letter it pairs with forces a chain of assumptions about the day's secret settings. The Bombe raced through candidate rotor positions, followed each position's assumptions to their electrical consequences, and discarded any that led to a contradiction, searching by elimination, not exhaustion. Later, his colleague Tommy Flowers built Colossus, the first programmable electronic digital computer, used to break the higher-level Lorenz cipher used by Hitler's high command. These machines were special-purpose, not Turing machines in his theoretical sense, but they proved that mechanical computation worked at scale.

Fig 1.2 · Enigma · one key, a different lamp every press

The same key, pressed three times, lights three different lamps: each press steps the fast rotor, so the current takes a new path out and, after the reflector, a different one back. The reflector also guarantees that no letter is ever enciphered as itself, the flaw the Bombe exploited.

How it works
  1. Press. The fast rotor steps one position first, so its wiring meets the contacts differently every time.
  2. Out. The current runs through the three rotors, each a fixed scramble of 26 wires.
  3. Turn. The reflector pairs contacts and sends the current back through the rotors on another wire.
  4. Lamp. It arrives at a different letter, and never at the one pressed.
  5. The settings. Rotor order, start positions and plugboard pairs gave about 158 × 1018 possible settings, changed daily.

Historians estimate Bombe and Colossus shortened the war by two years and saved roughly fourteen million lives. The question after the war became how to build a machine that isn't purpose-built for a single problem: a universal machine, Turing's theoretical idea, in actual hardware.

Historical note. Turing was prosecuted for homosexuality in 1952, sentenced to chemical castration by court order, and died in 1954, officially by cyanide poisoning, likely suicide. He never saw the computer revolution he made possible. Britain issued a formal apology in 2009. He now appears on the £50 note.

02 · The Transistor

Everything is sand

The first general-purpose electronic computer, ENIAC (1945), was built from vacuum tubes: glass bulbs that controlled electrical current using a heated filament inside a vacuum. ENIAC had 17,468 of them. It filled a room thirty metres long, weighed thirty tons, consumed 150 kilowatts (enough to dim the lights of Philadelphia when it switched on), and broke down on average every two days because a tube would burn out.

To make computers smaller, faster, more reliable, and affordable, the vacuum tube had to go. Its replacement was invented in 1947 at Bell Labs in New Jersey by three physicists: William Shockley, John Bardeen, and Walter Brattain. They called it the transistor, a contraction of transfer resistor.

Fig 1.3 · The replacement · the same switch, without the fire

A vacuum tube and a transistor do the same job: a small control signal decides whether a much larger current flows. The transistor does it in a sliver of silicon, with no glass, no glowing filament and nothing to burn out.

How it works
  1. Tube. A filament, kept hot, boils electrons off; the plate draws them across the vacuum; the grid between them, set by the control signal, lets them through or holds them back.
  2. Transistor. The control signal goes to the base, and current flows through the silicon between the other two terminals (the next figures open it).
  3. Why it won. A tube is hot, fragile and wears out: ENIAC's 17,468 tubes failed about every two days. A transistor has nothing to burn out, and it shrinks.

What a transistor actually is

A transistor is a switch with no moving parts, controlled by electricity rather than by a finger or a relay arm. It has three terminals: a base (or gate, in the modern field-effect design), a collector (or drain), and an emitter (or source). When you apply a small voltage to the base, it lets a much larger current flow between collector and emitter. No voltage at the base, no flow.

That is the entire mechanism under every computer ever built. Everything else is layers of abstraction over switches turning on and off: every program, every webpage, every video game, every neural network.

Fig 1.4 · Transistor as a switch · base off, base on

With no voltage on the base, no current flows between collector and emitter; with a small one, it does. Every computer is built from this one switch: a modern CPU holds roughly fifty billion of them.

How it works
  1. Three terminals. Collector and emitter carry the current; the base controls it.
  2. The threshold. In this kind of transistor about 0.7 V on the base opens the path; below it, almost nothing flows. In the field-effect transistors of modern chips the base is called the gate.
  3. The dots. Electrons, drifting from emitter to collector for as long as the base signal is there.

Why semiconductors

The transistor works because it is built from a semiconductor, a material whose conductivity sits between a conductor (like copper) and an insulator (like glass). A conductor is always on and an insulator always off; a switch is precisely a thing you can flip, so you need the in-between material, one that can be pushed either way. What lets you push it is doping: salting the pure silicon with a trace of another element. A dopant atom carrying one more outer electron than silicon leaves a spare electron free to wander; one carrying one fewer leaves a vacancy, a "hole", that a neighbouring electron can drop into, so the hole itself drifts like a positive charge. Either way the crystal gains mobile carriers, and once charge can be summoned or held back on command, a small voltage is enough to open or close a conducting path through the material. Almost all modern transistors are built from silicon, the second most abundant element in Earth's crust. Sand is mostly silicon dioxide. The entire digital economy is, in a literal sense, built on purified sand.

Fig 1.5 · Inside the switch · a field-effect transistor in cross-section

A positive voltage on the gate pulls electrons up under the oxide until they form a thin channel between source and drain, and current flows. The gate never touches the channel: its field reaches through the insulator, which is why these are called field-effect transistors.

How it works
  1. The silicon. The body is p-type silicon, doped with electron-accepting atoms; the source and drain are n-type, rich in free electrons. With the gate off, nothing joins them.
  2. The field. The gate's voltage acts across the oxide as an electric field. No charge crosses the insulator.
  3. The channel. The field gathers electrons under the oxide until that thin layer inverts, from p-type to n-type, and conducts.
  4. The name. MOSFET: metal-oxide-semiconductor field-effect transistor. Every modern CPU is a stack of these about 3 nanometres wide.

In 1958, Jack Kilby at Texas Instruments etched multiple transistors onto a single piece of germanium, creating the first integrated circuit. Within months, Robert Noyce at Fairchild Semiconductor independently did the same on silicon, with a more manufacturable process. Both filed patents. Noyce's process became the basis of the entire industry.

In 1965, Gordon Moore, co-founder of Intel and a former colleague of Noyce, published the observation that the number of transistors that could fit on a single integrated circuit was doubling roughly every twelve months, and would likely continue to do so. He later revised this to every two years. This pattern, Moore's Law, held with remarkable accuracy for fifty years and drove the semiconductor industry's roadmap. It is why your phone, with perhaps fifteen billion transistors, exists at all.

Fig 1.6 · Moore's Law · transistors per chip, 1971 to 2024

On a log scale steady doubling draws a straight line: from 2,300 transistors in 1971 to 28 billion in 2024. Since about 2015 the chips have fallen below the two-year line as transistors approach the size of atoms.

How it works
  1. The scale. Each gridline is ten times the one below, so growth at a steady rate of doubling is a straight line.
  2. The chips. 4004 (1971, 2,300) · 8086 (1978, 29 K) · 386 (1985, 275 K) · Pentium (1993, 3.1 M) · Pentium 4 (2000, 42 M) · Core i7 (2008, 731 M) · Epyc (2017, 19.2 B) · M4 (2024, 28 B).
  3. The line. Doubling every two years from the 4004. Across the whole span the chips doubled about every two and a quarter years.

03 · The Architecture

Von Neumann's insight: instructions are data

Early computers were hardwired. To set up a new calculation on ENIAC, its operators (almost all women, called "the ENIAC girls") unplugged and replugged cables for days. The hardware encoded the program. To change what the machine did, you changed the machine.

In 1945, John von Neumann, a Hungarian-American polymath who had worked on the Manhattan Project, circulated a paper called the First Draft of a Report on the EDVAC. It described a different architecture, one that would become the dominant design for every computer built afterward.

His insight: store the program itself in memory, alongside the data it operates on. Instructions are just patterns of bits. Data is just patterns of bits. The CPU reads instructions from memory exactly the same way it reads data, which means a program can read another program, modify it, and then run it. A machine can write programs.

This is the difference between a machine that does one thing very well and a machine that, given the right instructions, can do anything. The compiler that turns C code into machine code is a program. So is the web browser running on your computer, and so is the kernel that runs the browser. They all live as data in memory until the CPU reads them as instructions.

Fig 1.8 · Von Neumann architecture · one memory, one bus

One memory holds the program and the data it works on, and one bus carries both to the CPU, one at a time. Nearly every computer built since 1945 follows this design.

How it works
  1. Fetch. The program counter names the next cell; its instruction travels over the bus to the control unit.
  2. Execute. The instruction asks for data, which travels over the same bus; the ALU does the arithmetic: 5 + 3.
  3. Store. The result goes back up the bus into memory, and the counter moves on.
  4. One bus. Code and data share it, so they take turns: the bottleneck the next sections return to.

The Von Neumann bottleneck

The architecture's one famous weakness comes from its core design choice. Because instructions and data share the same memory, they share the same bus: the same physical wires between the CPU and main memory. The CPU can only do one transfer at a time. While CPUs got faster over the decades (clock speeds rose from kilohertz to gigahertz), main memory became faster much more slowly. A modern CPU can perform a basic operation in under a nanosecond. A round trip to main RAM takes about sixty nanoseconds. The CPU spends most of its time waiting.

The solution is a hierarchy of caches: small, fast memory built directly into the CPU that holds copies of recently used data. We'll cover them later in this chapter. This bottleneck is one of the deepest design constraints of modern computing, and almost every CPU optimisation since the 1980s has been an attempt to work around it.

04 · The CPU

Fetch. Decode. Execute. Repeat.

Every CPU ever built does the same four things in a loop, billions of times per second.

The instruction cycle is the fundamental unit of computation at the hardware level, a loop of four steps. A special register called the program counter holds the address of the next instruction to run. Fetch: the CPU reads the bytes at that address out of memory. Decode: it interprets that pattern of bits, working out which operation is being asked for and which registers or values it acts on. Execute: the unit that does the work (usually the ALU) carries it out, adding, comparing, or computing an address. Writeback: the result is stored back into a register or memory, and the program counter advances to the instruction that comes next. Then the cycle starts over, on every core, without pause. Everything else is a sequence of instructions fed through this one loop: your operating system, your browser, your music, this page.

Fig 1.9 · The instruction cycle · fetch, decode, execute, writeback

Every core runs this loop: fetch the instruction the program counter names, decode it, execute it, write back the result, and move the counter on, billions of times a second.

How it works
  1. Fetch. Read the bytes at the address in the program counter.
  2. Decode. Work out the operation and its operands from the bit pattern (Fig 1.10 takes one apart).
  3. Execute. The ALU or another unit does the work: an addition, a comparison, an address.
  4. Writeback. Store the result and move the counter on by the instruction's length: 5 bytes, then 3. A jump sets the counter instead, which is how this program loops.

What an instruction actually is

At the hardware level, every instruction is a binary number, a specific pattern of ones and zeros. The CPU's control unit is a circuit that, when given a particular pattern, activates a particular sequence of internal signals. The mapping from binary patterns to operations is called the instruction set architecture, or ISA. Intel and AMD CPUs use the x86 ISA. Apple Silicon Macs, your phone, and the Raspberry Pi use ARM. The two are incompatible: code compiled for one will not run on the other unless translated.

Assembly language is a human-readable label for these patterns, and the translation is one-to-one. The mnemonic mov eax, 5 is the assembler's name for the binary instruction 10111000 00000101 00000000 00000000 00000000 on x86. We will spend all of Chapter 3 on this.

One instruction as the CPU sees it: the first byte says what to do and to which register, the next four hold the value, lowest byte first.

How it works
  1. Opcode. B8 is 10111 000. The top five bits mean “move a 32-bit value into a register”; the bottom three name the register, and 000 is EAX.
  2. Value. x86 is little-endian: it stores the lowest byte first, so 5 sits in memory as 05 00 00 00.
  3. Decode. The decoder is a circuit that recognises these bit patterns and routes them to the right units; nothing is looked up by name.

Pipelining and parallelism inside one core

A naive CPU would run one instruction through every step of the cycle before starting the next. Modern CPUs use pipelining instead, overlapping the stages of different instructions, like an assembly line. While instruction 3 is being executed, instruction 4 is being decoded, and instruction 5 is being fetched. A modern pipeline may have 14 to 20 stages.

Fig 1.11 · Pipelined execution · five instructions, five stages

Five instructions of five stages each, overlapped like an assembly line: they finish in 9 cycles instead of 25, and once the pipeline is full one instruction completes every cycle.

How it works
  1. The stages. IF fetch · ID decode · EX execute · MEM memory access · WB writeback.
  2. The diagonal. Each instruction starts one cycle after the one before, so in any column every stage is busy with a different instruction.
  3. Beyond this. Modern CPUs also duplicate stages and finish several instructions in one cycle.

They also use out-of-order execution. If instruction 5 doesn't depend on instruction 4's result, the CPU may execute 5 first while 4 waits for memory. Speculative execution goes further: at a branch (an if statement) the CPU guesses which way it will go and starts executing that path before the condition has been computed. If it guesses right, it saves time. If it guesses wrong, it discards the work. Modern CPUs guess right about 95% of the time.

Fig 1.12 · Speculative execution · the CPU guesses, then checks

At a branch the CPU guesses which way it will go and runs ahead; a right guess keeps the work, a wrong one throws it away and takes the other path. Thrown-away work can still leave its mark in the cache: the trace that Spectre and Meltdown read.

How it works
  1. Why guess. Waiting for the condition would leave the pipeline idle for many cycles.
  2. The guess. Made from the branch's history; modern CPUs are right about 95% of the time.
  3. The catch. Throwing work away rolls back the registers, not the cache. A load that should never have run leaves its data behind, and an attacker can time the cache to find it.

Spectre and Meltdown (2018). Two catastrophic CPU vulnerabilities discovered in nearly every fast processor made since the mid-1990s. They exploited speculative execution: when the CPU guessed wrong and discarded the work, traces of that work remained in the cache, where an attacker could measure them to read memory they should not have access to. Hardware has bugs too, and they are far harder to fix than software bugs. We will return to this in Chapter 15.

05 · The Kernel

Why the kernel had to be invented

In the early 1950s, running a program meant booking the entire computer for yourself. You brought your stack of punched cards to the machine room, the operator loaded them, the machine ran your program, printed the output, and you came back an hour later to read it. One program at a time. No sharing.

Fig 1.13 · Running a program in 1955 · one job, one user, one machine

One program had the whole machine: you handed in your cards, the operator ran the jobs one by one, and you came back an hour later for the printout. Between jobs, while the next deck was loaded, the most expensive machine in the building sat idle.

How it works
  1. A job. A deck of punched cards, roughly one line of program per card, carried to the machine room.
  2. The queue. The operator loaded decks one after another; each job had the whole computer while it ran.
  3. The cost. A bug meant new cards and another hour's wait, and the machine stood idle in the gaps: the waste time-sharing set out to remove.

As computers got faster and programs got longer, this became absurd. The CPU sat idle most of the time, waiting for slow input/output devices like punch card readers or magnetic tape drives. Universities started asking: can one program run while another waits for I/O? Can different users be logged in simultaneously?

The answer was yes, but only if something stood between the programs and the hardware to manage the sharing. That something became the operating system kernel. The trick that made sharing pay off is timing: the instant one program stops to wait on something slow (a disk, a keypress, a network reply) is precisely the instant the kernel can hand the idle CPU to a different program that has work ready. And once several programs are interleaved on one machine, something has to keep them from trampling each other. So the kernel is also the one program that always runs, owns the hardware, and forces every other program to ask its permission to touch anything in the outside world. Sharing and protection are the same job seen from two sides, and the kernel is the answer to both.

Fig 1.14 · Protection rings · user programs, the kernel, the hardware

Programs run in Ring 3 and cannot touch the hardware: a direct attempt is stopped by the CPU itself. To reach the disk a program makes a system call, a trap into the kernel in Ring 0, which does the work and returns, typically in under a microsecond.

How it works
  1. The rings. x86 has four privilege levels; operating systems use two: Ring 0 for the kernel, Ring 3 for everything else.
  2. Enforced in silicon. In Ring 3 the CPU itself refuses privileged instructions and the kernel's memory; no software stands in the way to be fooled.
  3. The way in. A system call jumps to an entry point the kernel registered at boot, so a program can ask but never choose where it lands. The Bridge at the end of this Part opens the mechanism.

The system call: crossing the boundary

When your Python script opens a file, it cannot touch the disk itself: running in Ring 3, it has no permission to talk to the disk controller. Instead it asks: open() in Python calls fopen() in the C library, which executes the system call, the one instruction whose whole job is to cross the boundary. The CPU switches to Ring 0 at an entry point the kernel registered in advance, the kernel checks permission and does the work, and your program gets back a numeric handle (a file descriptor). What the silicon must provide for that crossing to be safe (the trap, the saved state, the one door user code cannot re-aim) is the story of the Bridge that closes this Part. What the kernel does with the request once it arrives is Chapter 4's.

Your program never touched the hardware. It asked the kernel, the kernel decided. This is the entire foundation of operating system security. Without this hardware-enforced boundary, every program would have full access to every other program's memory, every file, every network packet.

UNIX and the kernels we still use

In 1969, at Bell Labs, Ken Thompson and Dennis Ritchie designed an operating system called UNIX, on a creed austere enough to fit four words: everything is a file. The keyboard, the network connection and the running process are all reached through the same few calls. UNIX became, directly or indirectly, the ancestor of nearly every operating system in current use: Linux, written from scratch by Linus Torvalds in 1991; macOS's XNU; iOS and Android; even Windows now ships a Linux subsystem. The architectural ideas it introduced (processes, file descriptors, the system call interface) define what an operating system is. Chapter 4 opens the kernel as a program; Chapter 5 tells the story of the language it is written in.

Why this matters for security. A privilege escalation attack is one in which an unprivileged process (your malicious program running in Ring 3) finds a way to gain Ring 0 access. If it succeeds, it has full control of the machine: it can read any file, watch any keypress, install any rootkit. Every major operating system has had privilege escalation vulnerabilities. The kernel is the most security-critical code on any computer. Part II's kernel chapter returns to this, and so does Part IV's unified security chapter.

06 · Memory

The hierarchy of forgetting

Memory in a computer is not one thing. It is a hierarchy of storage, managed at different levels by the CPU and the kernel, that grows larger, slower and cheaper the further it sits from the CPU. Each level holds a copy of part of the level below it.

The numbers below explain why optimising software is hard. The CPU performs an arithmetic operation in roughly 0.3 nanoseconds. A round trip to main memory takes 60 nanoseconds: two hundred times longer. A read from a fast SSD takes 50,000 nanoseconds, which is 167,000 times longer than a register access. Most of computer architecture for the past forty years has been about hiding this gap.

Each level down is bigger and far slower: at a scale where a register answers in one second, a hard disk takes six months. A cache keeps a copy of what was just read, so reading it again costs seconds, not minutes.

How it works
  1. The scale. One register access, about 0.3 ns, becomes one second; every other time keeps its ratio to it. Bar length is size on a log scale.
  2. A miss. The first read looks in L1, L2 and L3, finds nothing, and waits for RAM: about 60 ns.
  3. A copy. On the way back each cache keeps a copy of the data and its neighbours.
  4. A hit. The next read of the same data, or of data next to it, stops at L1: about 1 ns.
Why caches multiply speed

The hierarchy works because programs do not access memory uniformly. They keep returning to the same regions: looping over an array, calling a function repeatedly, reading the next word in a string. This is called locality of reference, and it is the reason a small fast cache speeds up a much larger slow memory. The math is simple:

Tavg = h · tcache + (1 − h) · tRAM

If 95% of accesses hit L1 cache (1 ns) and only 5% miss into RAM (60 ns), the average access time is 0.95 × 1 + 0.05 × 60 = 3.95 ns. Without the cache, every access would cost 60 ns. The cache makes the whole system roughly fifteen times faster, and the hit rate only has to be high, not perfect. The same calculation justifies every layer of the hierarchy: a small fast tier above a larger slow one, exploiting locality.

Peter Denning's working set theory (1968) made this rigorous, and every CPU since has been a refinement of the idea. We will see the same locality argument resurface in Part II's kernel chapter when we look at virtual memory and page caches, in Part III's web chapter when we examine DNS caching, and in Part IV's data chapter when we examine database buffer pools.

Virtual memory: the lie the kernel tells

When your program asks for memory, the kernel does not give it a real physical address. It gives a virtual address, which is a fiction. Your program believes it has its own private address space starting at zero, with gigabytes of memory available. So does every other program. They all think they own the machine.

Between the CPU and the RAM sits the Memory Management Unit (MMU), a dedicated piece of hardware that translates every virtual address to a physical one at the moment of access, guided by page tables the kernel maintains. That one sentence hides an entire machine. The silicon half (the walker, the translation cache, the fault that fires when a page isn't there) is shown by the Bridge that closes this Part. The software half belongs to Chapter 4: page faults used as features, files mapped into memory, a fork that copies nothing.

This achieves three things at once: isolation (no program can read another's memory because the translation tables for different programs map to different physical pages), flexibility (the kernel can move pages around in RAM, swap them to disk, or load them on demand from a file), and protection (the page tables also encode permissions for read, write and execute, and the MMU enforces them).

Buffer overflow attacks exploit the memory model directly. If a program writes more data than a buffer can hold, the extra bytes spill into adjacent memory. If that memory contains a return address (an address the CPU will jump to when the current function ends), an attacker who controls the input controls where the CPU jumps next. Three layered defences each cut a different link in that chain: a stack canary is a known value planted between the buffer and the return address, so an overflow must trample it on the way and the change is caught before the function returns; ASLR (Address Space Layout Randomization) reshuffles where code and data load on every run, so the attacker no longer knows which address to aim at; and DEP (Data Execution Prevention) marks writable memory as non-executable, so bytes smuggled into a buffer cannot run as instructions even if the CPU is redirected into them. We'll see exactly how each of these works at the assembly level in Chapter 3.

What you now understand

You have followed the chain from sand to software. Transistors, silicon switches controlled by voltage, combine into logic gates, then into integrated circuits, then into CPUs. The CPU runs an endless loop: fetch, decode, execute, writeback. It executes instructions encoded as binary patterns drawn from an instruction set architecture like x86 or ARM. Programs and data live together in the same memory, a design choice (Von Neumann's) that defines what a modern computer is. The kernel mediates between programs and hardware, enforcing isolation and security through privilege rings and virtual memory.

This is the substrate. Every chapter that follows builds on it. Chapter 2 goes deeper into a single layer of this stack: the layer where mathematics and electricity meet. We will look at why a computer must be binary, how George Boole invented the logic that runs on those binary signals, and how arithmetic emerges from a few simple gates. By the end of Chapter 2, you will understand at a physical level why 0.1 + 0.2 does not equal 0.3 in any modern programming language.

01 · Why binary

Why a computer can only count to two

You count to ten because you have ten fingers. The Babylonians counted to sixty because they used the joints of the four fingers on one hand (twelve) times the five fingers of the other (sixty). The Mayans used twenty, counting their toes. Every counting system in human history was shaped by the body using it. Computers count to two because they are made of switches, and a switch only has two states.

A common but wrong intuition is that computers use binary because it is simpler or more elegant. The real reason is physical: electricity reliably represents two states, but not many more. A wire either has a voltage above some threshold (call it 1) or it doesn't (call it 0). The CPU can tell "above the threshold" from "below the threshold" with very high reliability, even through electrical noise, voltage fluctuations and manufacturing variation.

Could you build a computer that used three voltage levels (low, medium, high) to represent three digits? Yes. The Soviet Union built one. The Setun, designed in 1958 at Moscow State University by Nikolay Brusentsov, used balanced ternary (digits −1, 0, +1) and was, in many mathematical respects, more elegant than binary. But it required three voltage levels to be told apart reliably, and that is where it lost: a wire carries some fixed span of voltage. Binary cuts that span with a single threshold, leaving one wide gap between "low" and "high". A value has to drift almost halfway across the whole range before it crosses the line and flips. Ternary has to fit three levels into the same span, which means two thresholds and much narrower bands between them; now a drift that binary would shrug off is large enough to push a level across a boundary into its neighbour. As components age and temperature swings, those small drifts are constant. Binary won not because it was theoretically superior, but because it left the most room for error before a bit changed its mind.

Fig 2.1 · Why binary survives noise · one threshold against two

The same wire, the same noise. With one threshold binary leaves each level a wide margin; with two, ternary squeezes its bands until a drift binary would shrug off reads as the wrong digit.

How it works
  1. A threshold. The reader decides a digit by which side of a threshold the voltage is on.
  2. The margin. Binary's single threshold sits halfway: a level must drift half the span to flip. Ternary's two thresholds leave each level only a sixth of the span on either side.
  3. The noise. Ageing parts and temperature swings make small drifts constant, so the wider margin won. Engineering, not mathematics, decided it.

A wire that is either on or off holds one bit, short for binary digit. One wire expresses two values; two wires, four; three, eight; n wires, 2n. Eight bits make a byte, enough to represent 256 distinct values. A modern CPU works internally with words 64 bits wide: 264 ≈ 18 quintillion values per word.

A note on counting

In any base b, an n-digit number can represent bn distinct values. A 3-digit decimal number ranges from 000 to 999, which is 10³ = 1,000 values. A 3-digit binary number ranges from 000 to 111: 2³ = 8 values. The growth is exponential in both; only the base differs. This is why computer memory grows so quickly with each added bit: adding one wire doubles the addressable space.

02 · Boole

The Victorian schoolteacher who reduced logic to algebra

George Boole, a shoemaker's son, was born in Lincoln, England, in 1815. He taught himself Latin at twelve, Greek at fourteen, and the major European languages by his late teens. By twenty-six, with no university degree, he was running his own school. By thirty-two, he was a self-taught mathematician publishing original papers in differential equations.

In 1847, he published a short book titled The Mathematical Analysis of Logic. Seven years later, he expanded it into An Investigation of the Laws of Thought. The thesis of these two works was, at the time, almost incomprehensible: logic, the discipline of valid reasoning, was a branch of algebra.

In Boole's algebra, the variables represent not numbers but truth values: propositions that are either true or false. The operations are not addition and multiplication but three of their own. AND, written like multiplication (A · B), is true only when both of its inputs are true. OR, written like addition (A + B), is true when at least one input is true. NOT turns true into false and false into true. A variable can take only two values, 0 (false) and 1 (true), and that constraint gives the algebra laws that would be errors in school algebra, A + A = A and A · A = A, because "true or true" and "true and true" are each still just true. Same symbols; different rules underneath.

"The design of the following treatise is to investigate the fundamental laws of those operations of the mind by which reasoning is performed; to give expression to them in the symbolical language of a Calculus…"

George Boole, An Investigation of the Laws of Thought, 1854

Boole died of pneumonia in 1864, aged 49, after walking three miles in heavy rain to give a lecture and then lecturing in soaking wet clothes; his wife put him to bed and, on the principle that "like cures like," allegedly threw buckets of cold water on him. He never saw electricity used in computing: he died thirty-three years before the electron itself was discovered. For seventy years his algebra was considered a beautiful but useless curiosity.

Shannon's master's thesis: the most consequential paper of the 20th century

Then, in 1937, a 21-year-old MIT graduate student named Claude Shannon wrote his master's thesis. He was working with electrical relay circuits: telephone-switch-like devices that could be open (no current) or closed (current flowing) based on another control signal. He noticed that the behaviour of these circuits could be described exactly by Boole's algebra. An open relay was 0. A closed one was 1. Wire two relays in series, one behind the other, and current can reach the far end only if both are closed. That is AND. Wire them in parallel, side by side, and current gets through if either one is closed. That is OR. And a relay built to spring open when its control signal arrives passes current only when the signal is absent. That is NOT. The three operations Boole had defined on paper were sitting there in the wiring.

Shannon showed that any proposition expressible in Boolean algebra could be built as a circuit of relays that physically computed it, and that a circuit could be simplified by simplifying its Boolean expression. Logic and electricity were the same thing. The thesis is widely considered the most important master's thesis ever written: without it, the universal computer Turing imagined could not have been built.

Fig 2.2 · Boole's algebra · Shannon's switches · the same AND

Boole's A · B, true only where both propositions hold, is the overlap of two circles; Shannon saw that two switches in series pass current only when both are closed. The same algebra, ninety years apart, is the AND gate in every CPU.

How it works
  1. Boole, 1847. Propositions as sets of cases: A · B, "A and B", is the set where both hold, the overlap.
  2. Shannon, 1937. His master's thesis showed relay circuits obey Boole's algebra exactly: closed is 1, open is 0.
  3. Series and parallel. Switches in series are AND; side by side they would be OR (Fig 2.3).

The deeper claim. Anything that can be computed (any function that takes some input and produces some output by following a finite procedure) can be expressed as a Boolean formula and built as a circuit of AND, OR, and NOT gates. This is the practical version of Turing's universality theorem. It is why the same hardware can run a calculator, a video game, and a neural network. They are all, at the bottom, Boolean expressions.

Universal gates: NAND alone is enough

A result due to Henry Sheffer in 1913: you don't need three different kinds of gates. A single gate type, NAND (NOT-AND), can be wired up to imitate all of them. A NAND is an AND with its output inverted; it emits 0 only when both inputs are 1. Tie its two inputs together so the same signal A feeds both: it computes NOT(A · A), and since A · A is just A, the result is NOT A. You have built an inverter from one NAND. Run a NAND's output into a second NAND wired as that inverter and the two inversions cancel, leaving a plain AND. OR takes three NANDs arranged by De Morgan's laws so each input is inverted before a final NAND recombines them. Every gate, from one primitive. This is called functional completeness, and NAND is a universal gate.

In practice, this lets chip manufacturers build their fabrication process around a single gate type. Modern CPUs aren't literally made of just NANDs (there are also NOR, XOR, and other compound gates for efficiency), but the principle stands. One gate, repeated billions of times in different arrangements, is enough to compute anything computable.

Fig 2.4 · Everything from NAND · NOT, AND and OR built from one gate

NAND alone is enough: tie its inputs together and it is NOT, follow it with that NOT and it is AND, invert both inputs first and it is OR. From this one gate any circuit can be built, as Henry Sheffer showed in 1913.

How it works
  1. NAND. AND with its output inverted: 0 only when both inputs are 1. The bubble on the symbol is the inversion.
  2. NOT. With both inputs on A, NAND gives ¬(A · A), which is ¬A.
  3. AND. Invert a NAND once more: ¬(¬(A · B)) = A · B.
  4. OR. De Morgan's law: A + B = ¬(¬A · ¬B), a NAND of the two inverted inputs.
DeMorgan's Laws

Two identities of Boolean algebra, both due to Augustus De Morgan, a contemporary of Boole:

¬(A · B) = ¬A + ¬B

¬(A + B) = ¬A · ¬B

These laws say that you can move a NOT through an AND or OR by flipping the operator. They are how you simplify Boolean expressions, and how chip designers convert one kind of gate-level circuit into another. They reappear when we discuss filtering in databases (Chapter 13) and access control in security (Chapter 15).

A computer is a machine for arithmetic, yet at the level of voltages and gates it has no concept of "five" or "twelve." It knows only ones and zeros and Boolean operations on them. So how do we get from NAND to 5 + 3? One bit at a time.

The full adder, and adding wider numbers

Adding multi-bit numbers means handling the carry that passes from one bit position to the next. That needs a full adder: a circuit that takes three input bits (A, B, and a carry-in from the previous position) and produces a sum bit and a carry-out. It is built from two half adders and an OR gate: the first half adder adds A and B, the second adds that sum to the incoming carry, and the OR merges their two carry-outs into one, which is safe because the two can never fire together.

To add two 8-bit numbers, you chain eight full adders, the carry-out of each becoming the carry-in of the next; 64-bit numbers take 64. This design is called a ripple-carry adder, and modern CPUs use faster variants (carry-lookahead adders) built from the same simple gates.

The Arithmetic Logic Unit, the ALU you saw inside the CPU diagram in Chapter 1, is a circuit of adders plus logic for subtraction, multiplication, and bitwise operations. Every numerical operation a computer performs is a Boolean expression.

Adding 5 + 3: four full adders, one per bit, the least significant on the right. Each must wait for the carry from its neighbour, so the carry ripples left and the answer, 1000, settles one bit at a time.

How it works
  1. A full adder. Adds two bits and a carry-in, and gives one sum bit and a carry-out (Fig 2.6 opens one).
  2. The ripple. Bit 0: 1 + 1 = 0, carry 1. Bits 1 and 2: the carry makes 0 again, carry 1. Bit 3: the carry alone gives 1.
  3. Wider numbers. A 64-bit add is 64 of these in a row. Real CPUs use carry-lookahead designs so they need not wait for the ripple.
Fig 2.6 · Inside a full adder · two half adders and an OR

A full adder is two half adders and an OR. A and B meet in the first; its sum meets the carry-in in the second, which gives the sum bit; either half adder's carry becomes the carry-out.

How it works
  1. Half adder. XOR gives the sum of two bits, AND their carry: 1 + 1 is 0, carry 1.
  2. Adding the carry. The second half adder adds the incoming carry to the first sum.
  3. One carry out. The two half adders can never both carry, so an OR is enough. Chain four of these and you have Fig 2.5.
05 · Negative numbers

Two's complement, or how to subtract by adding

Computers don't natively understand negative numbers. There is no transistor that represents "minus." So how does your laptop store the value −5?

The naive approach, sometimes called signed magnitude, is to reserve one bit (usually the leftmost) as a sign indicator. 0 means positive, 1 means negative; the remaining bits represent the magnitude. So in 8 bits, 00000101 is +5 and 10000101 is −5. Simple, intuitive, and almost never used.

Why not? Two reasons. First, you end up with two zeros, 00000000 and 10000000 ("positive zero" and "negative zero"), which makes equality testing awkward. Second, and far worse, the ordinary adder gives the wrong answer. Feed it +5 (00000101) and −5 (10000101), and out comes 10001010, which reads back as −10, not 0. The adder has no idea the leftmost bit is a sign; it just adds it in. Making signed magnitude subtract correctly would take a separate, more complex circuit that inspects the sign bits first and decides what to do, and every extra circuit costs transistors, area, heat and money.

The trick: complement

The solution, used by every modern computer, is called two's complement. To represent a negative number in n bits:

Step 1Take the binary representation of the positive number
Step 2Flip every bit (0→1, 1→0). This is "one's complement."
Step 3Add 1 to the result. This is "two's complement."

So in 8 bits, +5 is 00000101. Flip the bits to get 11111010, add 1, and 11111011 is −5.

With this representation, subtraction is just addition. To compute 7 − 5, the CPU computes 7 + (−5) on the same adder circuit it uses for every other addition. The bits line up by arithmetic, not luck: flip-and-add-one turns a number x into 2n − x. (In 8 bits, −5 came out as 11111011, which is 251, and 251 is exactly 256 − 5.) So when the adder computes a + (−b), what it really adds is a + (2n − b), which equals 2n + (a − b). That extra 2n is a 1 sitting in bit position n, one place to the left of the widest bit the register can hold. It falls off the end and is discarded, and what remains in the register is precisely a − b.

Fig 2.7 · Computing 7 − 5 = 2 with two's complement

To subtract 5 the CPU adds −5, written in two's complement, on its ordinary adder. The sum has a ninth bit the register cannot hold; it falls off, and what remains is exactly 7 − 5.

How it works
  1. Making −5. Flip every bit of 5 (00000101 → 11111010) and add 1: 11111011.
  2. Why it works. 11111011 is 251, which is 256 − 5. Adding it adds 256 and takes away 5.
  3. The lost 256. 256 is the ninth bit. An 8-bit register has no place for it, so it is dropped and the answer is 2. There is no separate subtractor in any modern CPU.

An n-bit two's complement number ranges from −2n−1 to 2n−1 − 1. For 32-bit signed integers, that's roughly −2.1 billion to +2.1 billion. There is one more negative number than positive because 0 takes up one of the "positive" slots.

Fig 2.8 · The two's-complement wheel · where addition wraps

The 256 values of a signed byte sit on a wheel, not a line: adding 1 turns the pointer one notch. At the bottom +127 + 1 silently becomes −128; at the top −1 + 1 becomes 0, the same wrap that makes subtraction free in Fig 2.7.

How it works
  1. The slots. 0 at the top, positives clockwise to +127, negatives counter-clockwise from −1 to −128. There is one more negative than positive because 0 takes a "positive" slot.
  2. The seam. 01111111 + 1 = 10000000: the top bit flips, and a top bit of 1 means negative. Nothing in the hardware complains.
  3. Every width. 32- and 64-bit integers have the same wheel, with about 4 billion and 18 quintillion slots.

Integer overflow vulnerabilities. Because the range is finite, adding two large positive numbers can produce a negative result: the carry overflows the most significant bit and changes the sign. In 1996, an Ariane 5 rocket exploded 37 seconds after launch because a 64-bit floating-point velocity value was converted to a 16-bit signed integer that overflowed. Cost: $370 million. In security, integer overflow bugs are a classic source of buffer overflows: a length check using a signed integer can be tricked into accepting an enormous "negative" length that bypasses bounds checking. 06 · Floating point

Why 0.1 + 0.2 ≠ 0.3

Open any programming language. Type 0.1 + 0.2. The answer will not be 0.3. It will be 0.30000000000000004, in Python, JavaScript, C, Java and Rust alike. This is not a bug in any one language. It is a consequence of how computers represent fractional numbers.

The cause is the binary representation of fractions. A binary fraction is a sum of halves, quarters, eighths (negative powers of two) and nothing else. So a fraction can be written out exactly in binary only when its denominator is itself a power of two. 0.5 is 1/2 and 0.25 is 1/4, so both are clean and finite. But 0.1 is 1/10, and 10 = 2 × 5 carries a factor of 5 that no stack of halves can ever divide evenly, so its binary expansion never terminates. It runs 0.0001100110011001100..., the pattern 0011 repeating forever, for exactly the reason 1/3 repeats as 0.333... in decimal: 3 divides no power of ten, just as 5 divides no power of two. Computer memory is finite, so the endless expansion has to be cut off, and the remainder becomes a tiny error.

IEEE 754: the universal floating-point standard

In 1985 the IEEE published standard 754, which defines how all modern processors represent fractional numbers. Before the standard, every CPU did it differently, and numerical code was a portability nightmare.

A 64-bit "double precision" float divides its 64 bits into three fields, in a structure that mimics scientific notation:

Fig 2.10 · IEEE 754 double precision · sign, exponent, mantissa

A double is binary scientific notation: a sign, an 11-bit exponent stored 1023 too high so it can be negative, and 52 bits of mantissa after an implied leading 1. Here 6.5 and −0.75 are read straight off their bits.

How it works
  1. Sign. 0 is positive, 1 negative.
  2. Exponent. Stored with a bias of 1023: 1025 means 2², 1022 means 2⁻¹. Eleven bits give a range of about 10⁻³⁰⁸ to 10³⁰⁸.
  3. Mantissa. The digits after the binary point of 1.M; the leading 1 is implied, never stored. Fifty-two bits give 15 to 17 decimal digits.
  4. Single precision. The 32-bit float is the same with 1, 8 and 23 bits.

The 52 bits of mantissa give about 15 to 17 decimal digits of precision; the 11-bit exponent gives a dynamic range of about 10−308 to 10308. Most decimal fractions fit no finite binary expansion, so a double stores the nearest representable binary fraction, with a tiny rounding error.

When you compute 0.1 + 0.2, the CPU adds two slightly imprecise binary values and produces a slightly imprecise 0.3, but not the same one you'd get if you stored 0.3 directly. The errors don't cancel.

0.1 never fits in binary: its digits repeat forever, so the double keeps the nearest 52-bit fraction, and 0.2 likewise. Their sum lands one representable step above where 0.3 itself is stored; the error was in the inputs, not the addition.

How it works
  1. Why it repeats. 0.1 is 1/10, and 10 has a factor of 5 that no power of two can supply, just as 1/3 never ends in decimal.
  2. The grid. Doubles are not continuous. Near 0.3 neighbours are 2⁻⁵⁴, about 5.6 × 10⁻¹⁷, apart; the true 0.3 falls between two of them.
  3. The result. "0.3" is stored as the double just below it; the rounded 0.1 and 0.2 add up to the one just above. So in most languages 0.1 + 0.2 == 0.3 is false.
  4. Living with it. Compare floats within a tolerance, and count money in whole cents.

Special values: ±∞ and NaN

IEEE 754 reserves certain bit patterns for special values, because a calculation that runs off the rails should be able to keep flowing rather than halt the machine. When the exponent is all ones and the mantissa is zero, the value is infinity, which is what you get by dividing by zero (1.0 / 0.0) or by letting a number grow past the largest representable value, roughly 10308. The sign bit says which direction. When the exponent is all ones and the mantissa is non-zero, the value is NaN (Not a Number), the result of an operation with no meaningful answer at all, like 0.0 / 0.0 or sqrt(-1). And a NaN is built to spread: once one appears, any later arithmetic that touches it yields another NaN, so the bad result carries all the way through to the end of the computation, where it can be spotted, rather than crashing the program the instant it first arises.

NaN is not equal to anything, including itself. NaN == NaN evaluates to false in every IEEE 754-compliant language. That looks perverse until you remember what NaN means: no value at all. Two failed computations are not "the same number," because neither is a number; asking whether they are equal is as meaningless as asking whether two silences are the same note. And because a NaN is the one value not equal to itself, the test x != x is the standard, reliable way to catch one: the property that looks broken is the property that does the work.

Real-world consequences. Financial software cannot use floating point for currency, because rounding errors compound across millions of transactions. Banks use either integer cents or special decimal types instead. The 1991 Patriot missile failure during the Gulf War, which killed 28 American soldiers, was traced to a timing error, 0.1 rounded in binary, that accumulated over 100 hours of operation, causing the missile to miscalculate the position of an incoming Scud. Floating point is precise enough for almost everything, but its errors are real, and they compound.

Fig 2.12 · The Patriot missile · a clock that lost a third of a second

A Patriot battery near Dhahran had run for 100 hours, counting time in tenths of a second, and 0.1 rounded in binary made every tick a hair short. The clock fell 0.34 s behind, about 570 m at a Scud's speed, so the radar looked in the wrong place and the battery never fired; 28 soldiers died.

How it works
  1. The tick. 0.1 repeats forever in binary (Fig 2.11). The system held it in a 24-bit fixed-point register, chopped, so each tick counted about 0.000000095 s too little.
  2. The sum. 100 hours is 3.6 million ticks; 3.6 million × 0.000000095 s ≈ 0.34 s.
  3. The window. The radar predicts where a target will be and looks only there. With the clock 0.34 s behind, the window was some 570 m from the Scud, on 25 February 1991.
  4. The fix. Corrected software reached Dhahran the next day. Rebooting the battery would have reset the drift.

What you now understand

You have followed the layered chain from electricity to mathematics. A wire that can be on or off gives you a bit. Combinations of bits give you binary numbers. Boolean algebra, invented in 1847 by Boole and applied to circuits in 1937 by Shannon, describes operations on those bits. Logic gates are physical implementations of Boolean operations: AND, OR, NOT, XOR. Combinations of gates implement arithmetic: half adders, full adders, ALUs. Two's complement makes subtraction free. IEEE 754 extends the system to fractional numbers, with the unavoidable cost of finite precision.

Every higher-level abstraction in computing, from a Python list to a TLS handshake to a neural network, is built on top of these primitives. We will look at how the CPU actually executes a program, how function calls work at the metal, what a "stack" really is, and how attackers exploit the gap between what programmers intend and what their compiled code actually does.

01 · ISA

An instruction is a contract

In 1978, Intel released the 8086, a 16-bit chip whose instruction set no descendant has ever removed. Every x86-64 processor sold today still recognises the same core binary patterns Intel encoded that year. A processor doesn't run C, or Python, or JavaScript. It runs a sequence of binary patterns drawn from a specific menu: the instruction set architecture, or ISA. The ISA is the contract between hardware and software: hardware promises to execute every pattern in the menu correctly; software promises to use only patterns from the menu. Everything else (every compiler, every operating system, every program) sits on top of this contract.

Three ISAs dominate the world. x86-64, the direct descendant of that 1978 Intel line, runs essentially every PC and most servers. It is complex, with thousands of instructions accumulated over four decades of backward compatibility. ARM, designed by Acorn in the 1980s and now licensed by nearly every phone manufacturer, is the modern alternative: cleaner, more efficient, and the architecture of every iPhone, every Apple Silicon Mac, and every Android device. RISC-V, from Berkeley in 2010, is an open standard: anyone can build a RISC-V chip without paying licensing fees, and it is gaining ground in academia, embedded systems, and increasingly in industry.

Fig 3.1 · Same operation · three ISAs · three encodings

"Add 5 to a register" in the three instruction sets that run the world: the same three ingredients, an opcode, a register and the number 5, packed into 32 bits in three different orders. Each pattern is meaningless to the other two chips.

How it works
  1. x86-64. Variable length, 1 to 15 bytes. Here a prefix (64-bit), the opcode, a byte naming rax, and the 5 in one byte. With a 32-bit immediate it would be 7 bytes.
  2. ARM64. Every instruction is exactly 32 bits; this one is opcode, a shift bit, the 12-bit immediate, then source and destination registers.
  3. RISC-V. Also 32 bits, in another order: immediate first, opcode last. The base ISA has only six formats.
  4. The order of the bits. x86 is shown byte by byte as stored; ARM64 and RISC-V as 32-bit words, high bit on the left.

Because the encodings differ, an x86 binary will not run on an ARM CPU and vice versa, so the shift from Intel x86 to Apple's ARM-based M1 in 2020 required Apple to ship Rosetta 2, a translation layer that rewrites x86 binaries as ARM ones before they run.

Fig 3.2 · Rosetta 2 · an Intel app, translated once for an ARM chip

Rosetta 2 let Intel apps run on Apple Silicon by translating their x86 code into ARM code once, on first launch, and caching it. Where x86 adds to memory in one instruction, ARM must load, add and store, so one line can become three.

How it works
  1. Ahead of time. Rosetta reads the whole executable on first launch, writes an ARM version, and caches it; later launches skip the translation. Translated code runs at roughly 80% of native speed.
  2. One for many. Any x86 sequence has some ARM sequence with the same observable result; the translator's job is to find it. The ARM shown here is a faithful translation, not Rosetta's literal output.
  3. The hard part. x86 promises a stricter order for memory operations than ARM. Apple's chips have a mode that enforces x86's order while translated code runs, so multithreaded programs behave as they did on Intel.

RISC vs CISC, and why the war ended in a draw

In the 1980s there was a vigorous debate. CISC (Complex Instruction Set Computers, like x86) had hundreds of specialised instructions, including multi-step operations like "load from memory, add, and store back" in a single instruction. RISC (Reduced Instruction Set Computers, like ARM, MIPS, SPARC) had a small set of simple, uniform instructions. RISC machines could clock faster, and the reason is decoding. A variable-length instruction hides its own length. Fig 3.1's x86 add spent seven bytes, and other encodings of the same operation run anywhere from two bytes to a dozen, so the decoder cannot even find where the next instruction begins until it has finished parsing this one. Fixed-width instructions, always four bytes on ARM, sit at known boundaries, so the CPU can locate and decode a whole run of them at once, and each decode step stays simple enough to fit inside a shorter clock tick.

By the 2000s the debate was over, and both sides had quietly converged. Modern x86 CPUs internally translate complex CISC instructions into simpler RISC-like micro-operations (μops) and execute those. They pay the hard variable-length parse once, then serve hot code from a small cache of already-decoded μops. Modern ARM chips have grown more complex, with specialised instructions for cryptography, vector math, and machine learning. What still divides x86 and ARM is the binary incompatibility: the patterns of bits mean different things on different chips.

02 · Registers

The CPU's tiny notebook

Registers are the smallest, fastest level of the memory hierarchy from Chapter 1: a few dozen tiny storage cells inside the CPU core itself. Memory is too slow to operate on directly, so the CPU's instructions work primarily on registers. To add two numbers from memory, the CPU first loads them into registers, adds the registers, and stores the result back.

x86-64 has 16 general-purpose registers, each 64 bits wide. Their names carry historical baggage: in 1978 the original 8086 had 16-bit registers named AX, BX, CX, DX. When Intel went to 32 bits in 1985, they prepended an "E" for extended, giving EAX, EBX, etc. When AMD pushed to 64 bits in 2003, they replaced "E" with "R": RAX, RBX, RCX, RDX. The names persist; the chip remembers.

Fig 3.3 · The x86-64 register file · 16 + 2 + 45 years of names

x86-64 has sixteen 64-bit general-purpose registers: the original "A, B, C, D" set from the 8086, the "source/destination index" pair RSI/RDI, the stack-frame pair RBP/RSP, and the eight registers R8–R15 added by AMD64 in 2003. Plus two non-general-purpose registers: RIP, the instruction pointer, and RFLAGS, which holds the condition codes after every arithmetic operation. The right panel zooms into RAX. Because every generation of x86 had to remain backward-compatible with the previous one, RAX still contains the bits that were called EAX in 1985, AX in 1978, and AH/AL when split into bytes. Writing AL changes only the bottom 8 bits of RAX, leaving the rest untouched. That quirk has shaped C compilers, assembly-language style, and the encoding of the entire ISA.

RIP (the Program Counter, the address of the next instruction to execute) is itself a register, so changing what it points to changes what the CPU does next. That is the entire mechanism behind a function call, a loop, an if/else branch, an interrupt, and (as we'll see) a memory corruption exploit. If you control RIP, you control the program.

Fig 3.4 · System V calling convention · which register holds which argument

The System V AMD64 ABI (used by Linux, macOS, BSD) lays down which physical registers carry which arguments. The first six integer or pointer arguments go into RDI, RSI, RDX, RCX, R8, R9, in that order. The seventh argument and beyond are pushed onto the stack. The return value comes back in RAX. Floating-point arguments use a different set of registers (XMM0–XMM7), and structures larger than 16 bytes are passed by hidden pointer. The convention is what makes a compiled function callable from any other compiler, any other language, any other source file. Without it, every library linkage on every system would break.

03 · The stack

Memory that grows down

When a program starts, the operating system gives it a chunk of memory laid out in a specific pattern: its virtual address space. Among other regions, the OS reserves an area called the stack: a last-in-first-out buffer that grows as functions are called and shrinks as they return. By convention on x86-64, the stack lives at a high address and grows downward, toward lower addresses, as items are pushed.

Fig 3.5 · A process's virtual address space

A typical x86-64 Linux process address space. The kernel reserves the top half. The user-space portion contains, from high addresses down: the stack (function calls), unused space, the heap (dynamic allocations), the data section (globals), and the text section (read-only executable code). The stack and heap grow toward each other.

The CPU manages the stack with two instructions: push decrements RSP by 8 (one 8-byte value on a 64-bit machine), then writes the value to the address RSP now points to. pop reads the value at RSP and increments RSP back. The stack is the one data structure the ISA itself understands, built into the silicon rather than offered by a library.

Each function call creates a stack frame: a contiguous region of the stack containing that function's local variables, saved registers, and bookkeeping data. When the function returns, moving RSP back up discards the frame. There is no garbage to clean up: local variables vanish as soon as the function exits.

04 · Function calls

What "calling a function" actually means

Take the C line int result = add(5, 3);. The compiler first has to follow a calling convention, a contract between caller and callee about who puts arguments where, who saves which registers, and how return values are delivered. On Linux/macOS x86-64, that is the System V AMD64 ABI drawn in Fig 3.4; on Windows, it's the Microsoft x64 calling convention. The two differ slightly, but a function compiled for one ABI cannot be called from a program compiled for the other without a wrapper.

Under System V, add(5, 3) therefore receives its arguments in EDI and ESI and returns its result in EAX; the caller saves any volatile registers it cares about, and the callee preserves RBX, RBP, R12–R15.

C source 
int add(int a, int b) {
    return a + b;
}

int main() {
    int result = add(5, 3);
    return result;
}
x86-64 assembly (System V) 
; ---- function: add(int a, int b) ----
add:
    push   rbp             ; save caller's frame pointer onto stack
    mov    rbp, rsp        ; new frame pointer = current stack top
    mov    eax, edi        ; eax ← first arg (a, was in edi)
    add    eax, esi        ; eax += second arg (b, was in esi)
    pop    rbp             ; restore caller's frame pointer
    ret                    ; pop return address from stack, jump there

; ---- function: main() ----
main:
    push   rbp
    mov    rbp, rsp
    mov    esi, 3          ; second arg goes in esi
    mov    edi, 5          ; first arg goes in edi
    call   add                ; push return addr, jump to "add"
    ; --- after add returns, result is in eax ---
    pop    rbp
    ret

Two instructions carry the call: call and ret. call add does two things atomically: it pushes the address of the next instruction (the address of pop rbp in main) onto the stack, then sets RIP to the address of add. When add reaches ret, the inverse happens: ret pops the saved return address off the stack into RIP, and execution resumes in main at exactly the next instruction. Neither function sees the handoff; the stack remembers the call hierarchy beneath them.

Fig 3.6 · The stack during a function call

Three snapshots of the stack during a call. Each call instruction pushes a return address onto the stack; ret pops it. The pattern of saved frame pointers forms a linked list back through the entire call hierarchy, which is why a debugger can show you a "stack trace" listing every nested function call leading to the current point.

Why this matters. The return address is just a number stored in memory. The CPU has no way to verify it is the same number that was pushed there originally. If anything at all overwrites it between the call and the ret, the CPU will obediently jump wherever the new value points. This is the seam from which an entire era of computer security emerged.

05 · Buffer overflow

The bug that defined three decades of security

In November 1988, a 23-year-old Cornell graduate student named Robert Tappan Morris released a small program onto the early internet. It was meant to count machines. Within hours it had brought down roughly ten percent of every computer connected to the network (about six thousand machines). The vulnerability it exploited was a buffer overflow in the UNIX fingerd daemon. Morris became the first person convicted under the Computer Fraud and Abuse Act. The attack class he made famous is still, decades later, among the most exploited bugs in computing. To see why, trace what happens when a tiny C function's input doesn't fit.

C (vulnerable function) 
// A function that greets the user. Looks innocuous.
void greet(char *name) {
    char buffer[16];        // 16 bytes on the stack
    strcpy(buffer, name);   // copies until it hits a null byte
    printf("Hello, %s\n", buffer);
}

strcpy is the culprit. It copies bytes from name into buffer one at a time, stopping only at a null byte (a zero), and never checks whether buffer has room. If name is 17 characters long, the 17th byte lands one byte past the end of buffer, in whatever lives next in memory. On the stack, that is the saved RBP, and just past it, the return address.

Fig 3.7 · Stack frame of greet(): normal vs overflow

On the left, normal use: the buffer holds the input, the saved RBP and return address are intact, and the function returns to its caller. On the right, an oversized input keeps writing past the buffer, eventually overwriting the saved RBP and the return address. When ret executes, RIP gets loaded with whatever the attacker placed there.

From overwrite to code execution

Overwriting the return address is half the attack; the other half is choosing what to write there. The classic technique, perfected in the 1990s, is called shellcode injection: place machine code for a small payload (traditionally one that spawns a shell, hence "shellcode") into the buffer being overflowed, and overwrite the return address with the address of that shellcode. When the function returns, the CPU jumps into the buffer and runs the attacker's instructions.

A 1996 essay in the underground hacking magazine Phrack popularised the technique, turning it from rare expert knowledge into a cookbook.

"The objective of this paper is to show how to write buffer overflow exploits, using as an example a vulnerability in a real program. … The reader is expected to be familiar with C and assembly under x86 systems."

Aleph One, "Smashing the Stack for Fun and Profit," Phrack 49, 1996

Why C lets this happen

C, which gets its own chapter later, was designed in 1972 as a portable assembler. It exposes raw memory and raw pointers, and by default it does not check that array accesses stay within bounds. strcpy, gets, scanf("%s"), and many other standard-library functions assume the programmer has guaranteed the buffer is large enough. When they're wrong, the corruption is silent: bytes get overwritten, the program keeps running, and the consequence may not appear until a function returns into junk.

This is the price of memory unsafety. C and C++ are memory-unsafe by design, trading safety for performance and control. Modern languages like Rust, Java, Python, and Go are memory-safe: their runtimes or compilers check every array access against the array's real length, and they check before the write lands. An out-of-bounds access becomes a controlled failure (an exception, a Rust panic): the program stops loudly at the bad access instead of sailing on with a trampled return address, and a crash is not code execution. For Rust this guarantee was the whole reason the language exists; for Java, Python, and Go it came bundled with managed runtimes adopted for other reasons. Either way, the classical buffer overflow cannot occur.

Famous buffer overflow incidents. The Code Red worm (2001, IIS, infected 359,000 hosts in 14 hours). The SQL Slammer worm (2003, infected 75,000 servers in 10 minutes). The Blaster worm (2003, RPC). Heartbleed (2014, OpenSSL), technically a buffer over-read rather than overflow. The server trusted an attacker-supplied length field and copied back that many bytes from its own memory, so each reply spilled whatever happened to sit next to the buffer, including the private keys of millions of HTTPS servers. For decades, memory-corruption bugs accounted for the majority of critical CVEs (Common Vulnerabilities and Exposures). Microsoft, Google, and others have published data showing that around 70% of severe security bugs in their large C/C++ codebases trace back to memory unsafety. This is why Rust adoption is growing inside operating system kernels, Linux itself included as of 2022.

06 · Defences

The arms race the OS fought back

Operating systems and CPUs did not sit still. Beginning in the late 1990s, defences were added in layers. Each one closed a class of attack, was in turn worked around by attackers, and was followed by a more sophisticated defence.

Defence one: stack canaries

In 1998, Crispin Cowan introduced StackGuard, a compiler modification that placed a random value between local variables and the saved return address. The value was called a "canary," after the birds carried into coal mines to detect poison gas. Before each function returns, compiler-inserted code checks that the canary still holds its original value. If it has changed, because a buffer overflow trampled it on the way to the return address, the program aborts immediately.

This works as long as the attacker cannot guess the canary value. Modern compilers generate a random canary at program startup, so guessing is statistically infeasible. An attacker who can read process memory through a separate information leak, however, can sometimes recover it.

Fig 3.8 · The stack canary · a tripwire between buffer and return address

A stack canary is a randomly-chosen value placed by the compiler between local variables and the saved return address. The function's prologue writes the value; the function's epilogue, just before ret, checks that it has not changed. A buffer overflow that wants to overwrite the saved RIP must walk upward through memory, which means it must overwrite the canary first. When the epilogue's check fails, the program calls __stack_chk_fail and aborts before ret can transfer control. The defence assumes that the attacker cannot leak the canary value through some other channel, and it is one of several reasons modern programs make information disclosure a serious vulnerability class on its own.

Defence two: non-executable memory (DEP / NX bit)

Shellcode injection depends on the CPU executing bytes that sit in a buffer on the stack. The defence is to mark stack pages as non-executable. The CPU's MMU refuses to execute instructions from a page marked NX, raising a hardware exception instead. AMD added this to x86 in 2003 as the "NX bit" (No-eXecute); Intel followed; Windows calls it DEP (Data Execution Prevention), Linux keeps the name NX bit. Stack-injected shellcode immediately stopped working on systems with DEP enabled.

Defence three: ASLR

Even without injecting shellcode, attackers could redirect execution by overwriting the return address with the address of an existing function, such as the C library function system() with a string argument like "/bin/sh". This is called a return-to-libc attack. The countermeasure is ASLR, Address Space Layout Randomization. At each program launch, the operating system loads code, libraries, the heap, and the stack at random addresses. The attacker no longer knows where to point the overwritten return address. ASLR debuted in PaX (a Linux patch) in 2001, and became default on most operating systems by the late 2000s.

Fig 3.9 · ASLR · the same binary, three random load layouts

Three launches of the same executable, on the same machine, within seconds of each other. The .text segment, the heap, the libraries, and the stack each load at a different random address every time. An attacker who has overwritten a return address must guess where to redirect it. On 64-bit Linux the entropy is high enough (typically 28–30 bits for libraries, 24–28 bits for the heap, 30–32 bits for the stack) that brute-force guessing crashes the program long before a successful guess. ASLR is not perfect. Small entropy pockets, leaks of address fragments and partial overwrites can sometimes be exploited. Still, it raises the cost of every memory-corruption attack. It is, in a real sense, the reason modern software is roughly survivable.

Defence four, and the attack that still beat it: ROP

Hovav Shacham showed in 2007 that DEP and ASLR were not enough. He introduced Return-Oriented Programming (ROP). Instead of injecting new code, the attacker chains together short fragments of existing code in the program, fragments ending in a ret instruction. Each fragment, called a "gadget," does some tiny operation (load a register, increment a counter, write a byte). By stacking up the right sequence of return addresses on the stack, the attacker can build arbitrary computation out of the program's own code without executing anything new, which defeats DEP. Given large enough libraries, useful gadgets always exist somewhere.

ROP forced another layer: Control Flow Integrity (CFI, in which the compiler records where indirect jumps may legally land and the runtime refuses any transfer to an address off that list), shadow stacks (a separate, protected stack that mirrors the call stack and is checked on return), and ARM Pointer Authentication (which cryptographically signs return addresses, making forgery infeasible). Apple Silicon and recent Intel CPUs (CET, Control-flow Enforcement Technology) ship these defences in hardware.

Fig 3.10 · Return-Oriented Programming · arbitrary computation from existing code

Return-Oriented Programming, demonstrated by Hovav Shacham in 2007. The attacker still smashes the stack, but instead of injecting new code (DEP would forbid it), the new "program" is a sequence of return addresses, each pointing to a tiny gadget: a one-or-two-instruction snippet ending in ret, somewhere in the existing libraries. The first ret after the overflow pops the first gadget address into RIP. That gadget executes its tiny op, then its own ret pops the next gadget address from the stack, and so on. With a sufficiently large library, gadgets for any required operation can be found. Every program links libc, which has hundreds of thousands of bytes of code. ROP turned an entire field of defence (mark code non-executable) into a starting point. Modern hardware mitigations (CFI, shadow stacks, ARM PAC, Intel CET) are the response.

Fig 3.11 · The arms race, in one diagram

Each red dot is an attack technique that broke the previous defence. Each green dot is a hardware or compiler change that responded. The arms race continues, and at each step the cost of exploitation rises while the cost of a single mistake by a programmer in C or C++ falls more slowly.

The deeper lesson

Buffer overflows are not a bug in any one program. They are a structural consequence of a particular language model, one in which memory is raw, addresses are first-class values, and the programmer is responsible for every check. The defences above are mitigation, not a cure. The cure is to use a memory-safe language wherever possible. That so much critical infrastructure (operating system kernels, web browsers, database engines, network stacks) is still written in C and C++ is both a tribute to those languages' performance and a permanent source of risk. We will return to this when we discuss C, C++, and Rust in later chapters.

What you now understand

You have followed the chain from gates to assembly to exploits. The CPU executes a fixed menu of binary instructions defined by its ISA, whether x86, ARM or RISC-V, and everything else is a translation onto that menu. Registers are the CPU's tiny, fast notebook; the stack is a region of memory that grows downward and stores the bookkeeping of every function call. Calling conventions are the contract between caller and callee. Function calls work by pushing a return address onto the stack and jumping; they return by popping it back. And because the return address is just a number that lives in writable memory, an unchecked write (a buffer overflow) can replace it with anything, handing control of the machine to whoever supplied the input. The defences against this have evolved in lockstep with the attacks for thirty years: canaries, DEP, ASLR, CFI, pointer authentication.

So far every program has been free to do anything the silicon supports. Nothing yet stops a function from reading another program's memory, from writing to a disk it does not own, from monopolising the CPU until the user gives up. On any real machine, those things are not allowed. The Bridge that closes Part I is about why they are not allowed: what hardware features the silicon must already provide before any program can be made to behave, and how those few features combine into the conditions under which one program can be made to own the machine. We do not yet open the kernel and look inside it; that waits for Part II.

01 · User vs Kernel

One bit, two worlds

Of all the millions of bits inside a modern CPU, exactly one decides whether the next instruction runs at all. Software does not set it in the ordinary sense: the hardware does, in response to specific events, and no program in the lower mode can flip it. This single bit is the seam at which all of operating-system security begins.

The bit goes by different names on different chips. On x86 it is the bottom two bits of the CS selector, called the Current Privilege Level or CPL, with values 0 (most privileged) through 3 (least). On ARM it is the Exception Level, EL0 through EL3. On RISC-V it is the privilege mode field: U, S, M. Architectures offer different numbers of levels, but every operating system in use today reduces them to two: a privileged mode for the kernel, and an unprivileged mode for everything else. Books and conversations call these Ring 0 and Ring 3, after the original Multics and Intel terminology, even on architectures whose hardware has no rings at all.

The hardware enforces, not the operating system

What makes the arrangement work is that the silicon enforces the privilege bit, not software. When a program in Ring 3 tries to execute a privileged instruction, the CPU does not ask politely whether that is allowed. It does not consult a kernel table. It traps. The instruction does not execute; control is yanked from the program and handed to a piece of code at a fixed address, in Ring 0, that the kernel set up at boot. From the program's point of view, the next instruction simply did not happen, though the kernel may be about to terminate it.

Roughly thirty instructions are privileged on x86-64. They are exactly the instructions that would let a program break the operating system's abstractions if run from user space: those that load the page-table base register (MOV CR3), the interrupt descriptor table (LIDT) or the global descriptor table (LGDT); read or write model-specific registers (RDMSR, WRMSR); talk directly to physical I/O ports (IN, OUT); flush the translation cache (INVLPG); or halt the processor (HLT). User mode is defined by exclusion: it can do everything except these. The diagram below shows the division.

Fig BR.1 · The privilege bit · two worlds, one chip

The CPL field of the CS register holds the current privilege level. With CPL=0 (kernel mode) every instruction in the ISA executes normally. With CPL=3 (user mode) about thirty instructions are forbidden: the ones that would let a program reach past the operating system's abstractions. Attempting any of them does not return an error code; it raises a #GP fault in the hardware. The CPU stops the offending instruction mid-flight and jumps to a kernel handler whose address was registered in advance. The decision is made before the instruction takes effect, by the silicon itself.

How does the CPL get set in the first place? Boot starts in the most privileged mode the chip has, because there is no operating system yet and so no one to grant privileges. The bootloader hands control to the kernel, which is therefore born in Ring 0. The kernel then sets up the data structures the CPU will need to lower privilege when it launches the first user-space program: page tables that map user addresses, an interrupt descriptor table that handles future traps, a Global Descriptor Table whose code and stack segments mark Ring 3. Only then does the kernel execute the instruction (SYSRET on x86-64, ERET on ARM) that drops the CPU into user mode. From that moment on, getting back to Ring 0 requires going through the single mechanism the next section is about: the trap.

The privilege bit is not just a switch on instructions; it is a switch on memory access. Page-table entries are tagged with a U/S bit (user/supervisor), and pages tagged S are readable only when CPL=0. This is what stops a user program from poking around the kernel's data structures even by accident: the same hardware that enforces virtual-to-physical translation also refuses to translate a user-mode access into a supervisor-only page. Section 03 shows the page-table walker that does this.

Why this is the seam. Every protection the operating system claims to enforce (process isolation, file permissions, network sandboxing, container boundaries) bottoms out in this one bit. If a user-mode program could clear the bit by itself, the entire stack would collapse. It cannot, because the bit lives in silicon: it is set only by a small set of instructions that themselves require Ring 0 to execute. The whole tower of operating-system security stands on the bit's circular self-protection.

02 · The Trap

The one door between the two worlds

A user program eventually needs to do things only the kernel can do. Read a file. Open a socket. Print to the screen. The ISA has no READ_FILE opcode. What exists is one instruction that asks the kernel to do the thing on the program's behalf. The instruction is the system call, and the mechanism that delivers it across the boundary is the trap.

Unlike a function call, which jumps to an address the caller chose, a trap jumps to an address the kernel registered in advance, and which user code cannot change. All the user program knows is which instruction to fire (SYSCALL on x86-64, SVC on ARM, ECALL on RISC-V), and the silicon handles the rest: switch CPL to 0, save user-mode registers, jump to the kernel entry point, run the handler, then return to user mode at the next user instruction. From user space's perspective the syscall looks like any other instruction that took an unusually long time. From the kernel's perspective an entire round trip across the privilege boundary has just happened.

The path of one syscall

Fig BR.2 · The trap mechanism · one round trip across the boundary

A single system call, traced across the boundary. The user program runs ordinary instructions until it executes SYSCALL with the syscall number in RAX and arguments in the standard ABI registers. The CPU does five things atomically: it sets the privilege bit to 0, saves the user-mode RIP and RFLAGS, loads RIP from a model-specific register (MSR_LSTAR) the kernel set at boot, masks interrupts, and starts running. The kernel's entry stub looks up RAX in a syscall dispatch table, runs the handler, places the return value back in RAX, and executes SYSRET, which restores user state and jumps back to the instruction after the original SYSCALL. The whole round trip is typically under a microsecond. A typical desktop performs millions of these per second.

Traps, interrupts, exceptions: the same mechanism, three names

The system call is one case of something more general. Whenever the CPU must stop running the current code and run something the kernel chose instead, it takes this same path; only the name changes with the trigger. A system call is a synchronous trap initiated by the program. An exception is a synchronous trap caused by something the program did wrong: division by zero, a page fault, a #GP from Section 01. An interrupt is an asynchronous trap from a hardware device: a network card receiving a packet, a disk finishing a read, the timer firing. On x86, exceptions, interrupts and the legacy int 0x80 system call are all dispatched through one data structure: the interrupt descriptor table.

Fig BR.3 · The interrupt descriptor table · 256 doors into the kernel

When any trap fires, the CPU reads the IDT base address from its IDTR register, indexes by vector number, and jumps to the handler the kernel registered for that vector. The same table dispatches CPU exceptions (vectors 0–31), hardware interrupts from devices (vectors 32 and up), and on legacy x86 the int 0x80 system call. Exactly the same machinery underlies every involuntary entry into the kernel.

Each IDT entry carries a DPL (Descriptor Privilege Level) that controls whether user code can cause that vector to fire by software. Without the DPL, user code could spoof any kernel handler invocation by raising the corresponding interrupt by hand. The kernel sets DPL=3 only on the few vectors user code is meant to raise, such as the legacy syscall vector; the rest have DPL=0, which means a user-mode int 13 instruction does not deliver a fake general-protection fault, it raises a real one.

The kernel's authority is registered, not assumed. The CPU does not know what the kernel is. It knows where to jump on each kind of trap, because the kernel told it at boot by writing the IDT into memory and pointing IDTR at it. After boot, that pointer is in a privileged register that user code cannot change. The kernel's authority is an arrangement the kernel made with the silicon while it was still alone with the machine.

03 · The MMU

The hardware that draws the walls between processes

Memory isolation is not a software policy. If process A could simply read address 0x4000 in process B's space by asking, no firewall and no kernel subroutine could stop it. The read would already be done by the time the kernel found out. Isolation has to happen before any memory access completes. It does, because between the CPU and the RAM sits a small piece of silicon called the memory management unit, and every memory access flows through it.

Chapter 1 introduced virtual memory: each process believes it owns the entire address space, and the kernel maintains the illusion. The MMU is the part of the illusion that lives in hardware. It runs no code, kernel or otherwise; it is a circuit. Given a virtual address, it produces a physical address in nanoseconds, or it produces a fault.

The page-table walker as a hardware unit

Fig BR.4 · The MMU · silicon between the CPU and the RAM

The MMU is a piece of silicon between the CPU and the rest of the machine. On every memory access (load, store, or instruction fetch), the CPU hands the MMU a 64-bit virtual address and waits for a physical address back. The MMU first checks the TLB (a small associative cache of recent translations); on a hit, it returns immediately. On a miss, the page-table walker (a hardware finite-state-machine, not the kernel) descends four levels of page tables in main memory, starting from the address in CR3, and produces both a physical address and a set of permission bits. The permission bits are checked. If anything is wrong, the MMU raises a #PF (page fault, vector 14) and the kernel takes over. Wrong means a page not present, an S-tagged page touched from user mode, a write to a read-only page, or an NX-tagged page executed.

The kernel never runs the walk itself. It only writes the page tables (the data structures the walker reads), points CR3 at them, and lets the silicon do the lookup. Translation happens billions of times per second; if the kernel had to be involved in every access, the machine would not run at all. To switch between processes, the kernel changes that one register, and from that nanosecond on, every memory access made by the CPU resolves through a different process's tables. This is what process isolation actually is: a different value in CR3 means a different graph of page tables means different physical pages reachable from the same virtual addresses.

The TLB: a cache for translations

A four-level walk costs four memory accesses on top of the one the program asked for: a 5× tax on every load and store. No machine could afford that. So the MMU includes an associative cache called the translation lookaside buffer, the TLB, which remembers recent virtual-to-physical translations. The TLB is small (perhaps 64 to a few thousand entries on modern cores), but locality of reference means a hit rate above 99% is normal. The walker runs only on misses.

Fig BR.5 · The TLB · why the walk usually doesn't happen

A virtual address arrives at the MMU. The TLB is checked first; on a hit, translation is essentially free. The page-table walker runs only on a miss. Modern CPUs achieve TLB hit rates above 99% on typical workloads, which means the four-level walk, apparently a 5× tax on memory access, actually happens less than 1% of the time. The TLB is what makes paging affordable.

When the kernel changes a page-table entry (because a page got swapped out, say, or a permission was revoked), the TLB must be told, or it will keep serving the old translation. The instruction for this is INVLPG, which invalidates a single TLB entry: the next access to that virtual page misses the TLB and forces a fresh walk through the updated page tables. Extended across all CPUs that share the page tables, this is called a TLB shootdown, and it is one of the most expensive ordinary operations a kernel performs. INVLPG is privileged, so Section 01's #GP applies: a user process cannot mess with the TLB, even as a denial-of-service. The whole arrangement is enforced below, not above, the operating system.

04 · The Timer

The piece of silicon that makes multitasking possible

Imagine a CPU exactly like the modern ones (privilege bit, traps, MMU, all of it) but with no clock that fires interrupts. A cooperative kernel could still exist: programs would yield voluntarily, the kernel would schedule the next, and the world would mostly work. Until one program had a bug (an infinite loop, a slow algorithm, an attacker) and refused to yield. The machine would freeze, not because anything was broken, but because the kernel had no way to take the CPU back.

The piece of silicon that solves this is the hardware timer, a free-running counter wired directly into the interrupt controller. Every modern CPU has at least one. On x86 the local APIC timer ticks at the bus frequency and fires interrupts at a programmable rate; on ARM a generic timer does the same. The kernel programs it once, at boot (say, "interrupt me every millisecond"), and from then on, no matter what user code is doing, the timer fires and control returns to the kernel, which decides what to do next. Without this one piece of hardware, preemptive multitasking is impossible.

Fig BR.6 · The timer interrupt loop · how the kernel takes the CPU back

A typical second of CPU time, sliced by timer interrupts. The timer fires at a programmed rate (often 100–1000 Hz). Each tick raises an interrupt at vector 32, which dispatches into the kernel's scheduler. The scheduler chooses what runs next, which may be the same process or a different one. Process C is in an infinite loop and will never yield voluntarily; the timer is the reason that does not freeze the machine. Without this single piece of silicon, the kernel could only ask processes to yield, and any program that didn't would own the CPU forever.

Modern Linux can configure itself in three modes regarding the timer: HZ_PERIODIC (a tick at every fixed interval, the historical default), NO_HZ_IDLE (skip ticks when the CPU is idle, to save power), and NO_HZ_FULL (skip ticks even when running, used for high-frequency trading and scientific computing where each tick is an unwanted disruption). Whatever the mode, the mechanism underneath is the same: hardware that interrupts the CPU independently of the running program.

Why the timer is irreducible. Privilege rings, traps, and the MMU all give the kernel authority over what user code can do. The timer gives the kernel a chance to exercise that authority, even when user code never calls into the kernel. Multitasking, time-sharing, fairness, deadline scheduling, even the ability to kill a misbehaving program: all rest on this one circuit firing on a schedule the user cannot disable.

05 · Talking to the World

How the CPU reaches beyond itself

The CPU on its own can compute, but it cannot type, see, hear, or speak. To do anything observable, it has to communicate with devices: keyboards, screens, disks, network cards, audio chips, GPUs. The path from CPU to device is hardware too, and as with everything else in the Bridge, only the kernel gets to use it.

Two channels carry every conversation between CPU and device. The first is memory-mapped I/O: device registers sit at fixed addresses in the physical address space, and reading or writing those addresses is how the CPU talks to the device. The second is direct memory access: the device, on its own initiative, copies data into or out of RAM without asking the CPU on every byte. Both are coordinated by interrupts: the device tells the CPU "I'm done" by raising an IRQ, which goes through the same trap machinery from Section 02.

Memory-mapped I/O: devices live at memory addresses

Fig BR.7 · The physical address space · devices among the RAM

The CPU sees one flat physical address space. Some of those addresses are RAM; some are a video framebuffer; some are device registers on PCIe controllers; some are interrupt-routing chips; some are firmware ROM. The CPU doesn't know which is which. It just issues a load or a store. The chipset routes the access to the right place. To send a packet, the kernel writes to the NIC's MMIO region. To draw a pixel, the kernel writes to the framebuffer. To program the timer's tick rate, the kernel writes to the LAPIC's MMIO region. The same MOV instruction does all of these. Only the address differs. And only the kernel can map any of these regions into a process's address space (Section 03), so only the kernel can reach them.

DMA: when the device copies on its own

MMIO is fine for sending small commands ("read sector 4096 into buffer at 0x4a200000"), not for the data itself. A modern NVMe SSD reads gigabytes per second; if the CPU had to copy each byte one MMIO load at a time, the CPU would do nothing else, and the SSD would still be the slow part. The hardware solution is direct memory access: the device has its own memory-bus master, and once the CPU has told it where to read and where to write, the device shovels data on its own. The CPU runs something else until the device raises its completion interrupt and the kernel takes over to clean up.

Fig BR.8 · Direct memory access · the device writes RAM by itself

A typical disk read with DMA. Step 1: the kernel does a small MMIO write to the SSD's command register, telling it where to put the result. Step 2: the SSD reads its sectors and writes them straight into RAM, on the memory bus, without involving the CPU. The CPU is free to run other processes during this transfer. Step 3: when the SSD is done, it raises an IRQ; the trap machinery from Section 02 dispatches the kernel's interrupt handler; the kernel marks the I/O complete and wakes whichever process was waiting. For a multi-megabyte read this is the difference between using one core's full attention and using essentially none of it.

DMA has a security cost. A device that can write any address in RAM is dangerous: a malicious or buggy network card could overwrite kernel code. Modern systems address this with another piece of silicon, the IOMMU: a second MMU that translates and bounds-checks the addresses devices use, exactly as the regular MMU does for the CPU. A NIC can then be told it may DMA only into a specific buffer; an attempt to reach kernel memory raises a fault. The IOMMU is the reason VFIO and PCI passthrough into virtual machines is safe. 06 · Synthesis

What the kernel must therefore be

Part I has been building toward one question since Chapter 1, and we can now answer it without reading a single line of kernel source. Given what the silicon provides, what is the minimum program that turns five hardware features into the abstractions every modern computer offers?

Each abstraction we use without thinking corresponds, almost one to one, to a hardware feature from the previous five sections. No abstraction exists without silicon to enforce it, and no silicon is useful until a program, the kernel, sets it up correctly at boot. The diagram below maps the chain.

Fig BR.9 · Hardware features → kernel → abstractions

Read top to bottom: each hardware feature in the upper row enables one (or more) of the abstractions in the lower row. The kernel is the middle layer: the program that takes the raw silicon primitives and arranges them into something programs can use. Without the privilege bit, there is no root vs user. Without the trap, there is no system call API. Without the MMU, processes share one memory space. Without the timer, multitasking is impossible. Without MMIO and DMA, the CPU cannot reach beyond itself. The whole tower of modern operating systems sits on these five features and the few thousand lines of kernel that bind them together at boot.

The kernel as the smallest program that arranges the silicon

Note what this argument does not say: that the kernel is small, or that it does only what hardware demands. Linux is more than thirty million lines of code; macOS's XNU and Windows's NT are smaller but still vast. They contain filesystems, network stacks, GPU drivers, virtual machines, security frameworks, and the long tail of a thousand specialised subsystems. The silicon requires none of that, only a kernel that sets up page tables, registers a trap handler, programs a timer, and gets out of the way.

The rest is engineering, and that engineering is what Part II is about. It takes the kernel as a real program and asks the questions only code can answer: how should processes be scheduled? How should virtual memory be organised in software, on top of the hardware tables we now know about? What data structure connects a filename to a sequence of disk blocks? How do processes talk to each other? What goes wrong when the kernel itself has bugs?

But every one of them assumes, silently, that the bridge we have just walked across already exists. That somewhere underneath the schedule() function is a timer that called it. That somewhere underneath the read() system call is a SYSCALL instruction and an entry point the kernel registered at boot. That somewhere underneath every memory dereference is a four-level page-table walker doing the translation in nanoseconds. The kernel chapter that opens Part II will not stop to mention these things. They are what the Bridge is for.

The kernel is software. The reason the kernel can exist at all is hardware.
