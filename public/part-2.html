01 · Anatomy

The kernel is just a program

It is easy, after Chapter 1, to think of the kernel as some abstract authority, a governing law of the machine. It is not. The Bridge at the close of Part I showed the hardware contract that makes a kernel possible at all: the privilege bit, the trap, the MMU, the timer. On the kernel side of that contract is a program: a set of instructions stored in memory, executed by the same CPU that runs everything else. The Linux kernel, as of 2025, is roughly 30 million lines of C, with a small and growing amount of Rust. What makes it the kernel is not what it is made of, but where it sits, in Ring 0, with hardware-enforced privileges no other program has.

When you press the power button, the CPU starts executing instructions from a fixed address in the motherboard's built-in firmware, historically called the BIOS and now usually UEFI. The firmware initialises hardware, finds the boot device, and loads a small program called a bootloader (GRUB on Linux, Windows Boot Manager, iBoot on Apple devices). The bootloader's only job is to find the kernel image on disk, load it into memory, and jump to its entry point. From that moment, the kernel runs until the machine shuts down.

Monolithic vs microkernel: the great schism

Two philosophies of kernel design have been arguing since the late 1980s. A monolithic kernel puts everything in Ring 0: process scheduling, memory management, filesystems, device drivers, network stacks, all of it. Performance is excellent because subsystems can call each other directly, with no boundary crossings. The cost is fragility and security: a bug in any part of the kernel can corrupt the whole machine, and a single device driver with a vulnerability can be the entry point for total compromise. Linux is monolithic. Windows is monolithic. Most kernels in production use are monolithic.

A microkernel puts only the absolute minimum in Ring 0, typically just message passing, basic memory protection, and minimal scheduling. Filesystems, drivers, and network stacks all run as separate user-space processes that communicate via messages. A bug in a driver crashes only the driver, not the kernel. The cost is performance: every interaction crosses the user/kernel boundary, and message passing adds latency. Notable microkernels: MINIX (Andrew Tanenbaum's research OS), L4 (used in many embedded systems), seL4 (formally verified, meaning mathematically proven to have no kernel bugs of certain classes).

In 1992, Tanenbaum publicly criticised the then-new Linux on a USENET group, calling its monolithic design "obsolete" and "a giant step back into the 1970s." Linus Torvalds responded bluntly, and at length. Tanenbaum was correct in theory. Torvalds was correct in practice. The schism has never closed.

Fig 4.1 · The Tanenbaum–Torvalds debate, January 1992

In January 1992 Andrew Tanenbaum told comp.os.minix that Linux's monolithic design was obsolete; Linus Torvalds, twenty-two, answered at length. Three decades on both were right: microkernels hold the safety-critical niche, and Linux runs nearly everything else.

How it works
  1. Tanenbaum's case. Theory: a microkernel keeps drivers and services out of the kernel, so one bug cannot take the machine down. He also predicted Linux, tied to the 386, would not last.
  2. Torvalds's case. Running code: a monolithic kernel is simpler and faster, and Linux was free and worked on the machines people had.
  3. The outcome. Formally verified microkernels such as seL4 rule where one kernel bug is unacceptable; Linux runs servers, phones and supercomputers.

macOS sits in the middle. Its kernel, XNU, is a hybrid: a Mach microkernel core wrapped with a BSD UNIX layer that runs in the same address space, so you get message-passing primitives and monolithic-kernel performance. iOS uses the same kernel. Android uses Linux. Windows NT was originally microkernel-influenced but has drifted increasingly monolithic for performance reasons.

Fig 4.2 · Monolithic vs microkernel · speed against safety

A monolithic kernel runs everything in Ring 0, so a file read crosses the boundary twice; a microkernel runs file systems and drivers as separate programs, so the same read crosses eight times. The price buys safety: a driver bug takes down one process, not the machine.

How it works
  1. Monolithic. Scheduler, memory, file systems, drivers and network stack share one address space in Ring 0 and call each other directly.
  2. Microkernel. Ring 0 keeps only message passing, basic memory protection and scheduling; everything else is a user process that talks by IPC.
  3. The trade. Every crossing costs time, so microkernels are slower; every component outside Ring 0 is a bug that cannot corrupt the kernel, so they are safer.

Kernel modules: a third path

Linux softens its monolithic stance with loadable kernel modules (LKMs): drivers and filesystems compiled separately from the main kernel and loaded or unloaded at runtime with commands like insmod and rmmod. They still run in Ring 0, so a buggy module can crash the kernel, but they don't have to be linked into the main image. Most graphics drivers, filesystem drivers, and hardware support on Linux ship as modules; lsmod on a running system lists hundreds of them.

Fig 4.3 · A kernel module loading at runtime

insmod links a separately built module into the running kernel: its calls are resolved against the kernel's symbol table, its init function runs, and from then on it is part of Ring 0. rmmod takes it out again, so Linux stays monolithic in speed but modular in practice.

How it works
  1. Load. The kernel allocates memory for the module, copies its code in, and resolves every kernel function it calls by name in the symbol table.
  2. Start. It calls the module's module_init(); a driver registers itself with the subsystem it serves.
  3. Still Ring 0. A loaded module has the kernel's full power, so a buggy one can crash the machine (Fig 4.2).
  4. Unload. rmmod calls module_exit(), frees the memory and forgets the module. lsmod lists what is loaded.

Linux is a clean theoretical model modified by practical necessity: monolithic but modular. It runs in Ring 0 but increasingly delegates risky work (drivers in user space, eBPF in a verified sandbox, see Section 6) to safer compartments. The history of operating systems is the history of these compromises.

02 · Scheduling

The art of taking turns

A modern laptop runs hundreds of processes; a server may run thousands. Your machine has at most a few dozen CPU cores, so most processes cannot be running at any given instant. The kernel creates the illusion that they all are by switching between them many times per second, too fast for you to perceive the gaps. The component that decides which process gets the CPU next is the scheduler, one of the most-studied parts of any kernel.

Cooperative vs preemptive: who interrupts whom

The earliest multi-tasking systems were cooperative: each running program voluntarily yielded control back to the scheduler when it had nothing useful to do. Mac OS through version 9 worked this way, as did 16-bit Windows. The model is simple and lightweight, but one misbehaving program that never yields freezes the entire machine.

Modern systems are preemptive: the kernel forcibly takes the CPU back from a running process at regular intervals, ready or not. The mechanism is the hardware timer interrupt: a timer on the CPU core itself, introduced in the Bridge, programmed by the kernel to fire at a set rate (typically 100–1000 times per second on Linux). Each interrupt forces the CPU into Ring 0, where the scheduler runs and either resumes the current process or switches to a different one.

What "scheduling" actually has to decide

Picking a process to run sounds trivial, but each classical algorithm makes a different trade-off:

AlgorithmHow it worksTrade-off
FCFSFirst-come, first-served. Run processes in arrival order until they finish.Simple. Terrible response time: one long process blocks all the short ones (the "convoy effect").
SJFShortest Job First. Pick the process with the shortest remaining time.Provably optimal for average wait time. Requires knowing job length in advance, which you usually don't.

CFSCompletely Fair Scheduler. Linux's default 2007–2023. Tracks how much CPU each process has used; always runs whichever has used the least.Approximates "everyone runs at exactly 1/N speed on N processes." O(log N) per scheduling decision via a red-black tree.

Linux's CFS keeps every runnable process in a self-balancing binary tree (a red-black tree), keyed by virtual runtime, a measure of how much CPU time the process has consumed, weighted by its niceness. The next process to run is always the leftmost node of the tree (smallest virtual runtime). When a process runs, its virtual runtime increases; when it blocks, it's removed; when it wakes, it's reinserted with its saved value. The result is approximate fairness: every process tends toward equal CPU usage, and any process behind catches up first. Since kernel 6.6 (2023), Linux's default is CFS's successor EEVDF (Earliest Eligible Virtual Deadline First), which keeps the same virtual-runtime bookkeeping but gives every task an explicit deadline, so latency-sensitive work is scheduled on time rather than merely fairly.

Fig 4.4 · CFS chooses the leftmost node of a red-black tree

CFS keeps runnable processes in a tree ordered by virtual runtime, the CPU time each has had. The leftmost is the furthest behind, so it runs next; as it runs its virtual runtime grows, and it goes back in further right.

How it works
  1. Virtual runtime. CPU time received, weighted by priority. Whoever has had least is owed the CPU.
  2. The tree. A red-black tree, kept balanced, so finding the leftmost, removing it and inserting a process are all O(log N), even with thousands runnable.
  3. Since 6.6. Linux's default is now EEVDF, which keeps the same bookkeeping and adds a deadline per task so latency-sensitive work runs on time.
Fig 4.5 · Four schedulers, one workload

The same four jobs under four schedulers. Shortest-job-first gives the lowest average wait; round robin and MLFQ give up average wait to start every job almost at once, which is what an interactive machine needs.

How it works
  1. The jobs. "A 0+8" means A arrives at time 0 and needs 8 units of CPU. Every schedule here is simulated, not drawn by hand.
  2. FCFS. First come, first served: A's eight units hold up everyone behind it, the convoy effect.
  3. SJF. Shortest job first: provably the lowest average wait, but it needs to know job lengths in advance.
  4. Round robin. Each job runs for a quantum of 2, then goes to the back of the queue: responsive, at the cost of many switches.
  5. MLFQ. Multi-level feedback queue: a job that uses up its whole slice drops to a lower queue with a longer slice, so short jobs stay on top. Windows and classic UNIX schedulers work this way.
Queueing theory and Little's Law

The mathematics underlying scheduling is queueing theory, developed in the early 20th century by Agner Krarup Erlang for telephone networks. Its most important result is Little's Law:

L = λ · W

The average number of items in a queueing system (L) equals the average arrival rate (λ) multiplied by the average time each item spends in the system (W). It holds for any stable queue, regardless of arrival distribution or service distribution. It also explains why a slightly oversubscribed system produces explosive wait times: a queue drains at some service rate μ, and the only slack that absorbs a burst of arrivals is the spare capacity μ − λ. As λ climbs toward μ, each burst takes longer to drain than the quiet spell before the next one arrives, so backlog stops clearing between bursts and starts compounding, with the wait growing like 1/(μ − λ), a hyperbola, not a slope. It is why the difference between 95%-loaded and 99%-loaded servers is not 4%: it is often 10× in latency.

Fig 4.6 · Little's Law and the cliff at full utilisation

Little's Law ties a queue's length to its arrival rate and wait: L = λW, for any stable queue. As utilisation nears 100% the wait grows like 1/(1 − ρ): five times the bare service time at 80% load, twenty times at 95%.

How it works
  1. The law. Average number in the system = arrival rate × average time in it. It needs no assumption about how arrivals or service times are distributed.
  2. The curve. For the simplest queue (random arrivals, one server, called M/M/1) the time in the system is the service time divided by 1 − ρ.
  3. The cliff. From 50% to 60% load the wait grows by a quarter; from 90% to 95% it doubles; at 100% (the dashed line) the queue never drains. That is why operators worry once a server stays above about 80%.

Real-time scheduling: when missing a deadline kills

General-purpose schedulers like CFS optimise for average performance and make no guarantees about worst-case latency. For most software this is fine; for an anti-lock braking system or a pacemaker it is catastrophic. These systems run on real-time kernels: variants of Linux (PREEMPT_RT) or specialised OSes (VxWorks, QNX, FreeRTOS) that guarantee a task will run within a bounded time after it becomes ready, even under load. The mathematical foundation is rate-monotonic scheduling and earliest-deadline-first scheduling, analysed by Liu and Layland in a 1973 paper.

Fig 4.7 · A periodic task and the deadline it must meet

A real-time task must finish each job inside its period: here every 10 ms. Three jobs fit with room to spare; the fourth runs 12 ms and is still going at its deadline, which in a brake controller is a failure, not a stutter.

How it works
  1. Hard real time. Real-time kernels (PREEMPT_RT Linux, VxWorks, QNX, FreeRTOS) guarantee a ready task runs within a bounded time, even under load.
  2. The guarantee. Rate-monotonic scheduling meets every deadline if total utilisation stays under about 69%; earliest-deadline-first, up to 100% (Liu and Layland, 1973).
  3. The overrun. A job that takes longer than its budget breaks the arithmetic, which is why real-time code is written to bounded, measured worst cases.
03 · Virtual memory

The lie of unlimited memory

Chapter 1 introduced virtual memory as the kernel's mechanism for isolating processes: every process believes it has its own private address space starting at zero. The Bridge showed the MMU and TLB as the silicon that makes the mechanism enforceable. Here is the machinery that sustains the illusion: page tables built as trees so that 64-bit addressing is tractable at all, the TLB that caches their translations, and the page faults that quietly bring memory into existence on demand.

The translation problem

Every memory access a program makes uses a virtual address, but physical RAM is addressed by physical addresses. The Memory Management Unit (MMU), built into the CPU, translates virtual to physical on every load and store, using a translation table the kernel maintains: the page table.

Memory is divided into fixed-size blocks called pages, typically 4 KB: virtual pages in the address space and physical pages (often called "page frames") in RAM. The page table maps one to the other. When a virtual page has no physical page in RAM (it has never been used, has been swapped to disk, or belongs to a memory-mapped file not yet loaded), its entry is marked invalid, and the MMU raises a hardware exception called a page fault. The kernel's page-fault handler decides what to do.

Why the page table cannot be flat

A flat page table would hold one entry for every possible virtual page. On 64-bit x86, the architecture defines a 48-bit usable virtual address space (256 terabytes), giving 236 pages. At one 8-byte entry per page, the table alone would need 512 GB. Per process.

The solution is a multi-level page table: a tree. The 48-bit virtual address is split into four 9-bit fields plus a 12-bit page offset, and each 9-bit field indexes one level of a four-level tree. The address space is sparse (a process uses a tiny fraction of the 256 TB), so most branches are empty and never allocated: a real x86-64 process typically maps its memory with a few megabytes of page tables, not 512 gigabytes.

Fig 4.8 · x86-64 four-level page table walk

The CPU splits a 48-bit address into four 9-bit indices and a 12-bit offset, then follows CR3 down a tree of four tables, one index per level. Four table reads come before the data itself: five memory reads for one load, unless the TLB already holds the answer.

How it works
  1. Why 9 bits. A table is one 4 KB page of 8-byte entries, so it holds 512 of them, and 29 = 512. The last 12 bits address a byte inside a 4 KB page.
  2. The pointers. CR3 holds the physical address of the top table; each entry holds the physical address of the next table down, plus permission bits.
  3. Sparse by design. Tables exist only for regions the process uses, so a few megabytes of tables map a whole program. Newer CPUs can add a fifth level for 57-bit addresses.

The TLB: a cache for translations

Walking all four levels on every access would be ruinously slow: each memory access would become five (four for the table walk, one for the actual data). The fix is the Translation Lookaside Buffer (TLB), a small, very fast cache inside the CPU that stores recent virtual-to-physical translations; a typical x86-64 TLB has between 64 and 1500 entries. The CPU checks it first. If the entry is there (a "TLB hit"), translation takes one cycle; if not (a "TLB miss"), the MMU walks the page tables and inserts the result into the TLB.

Hit rates on the TLB are typically above 99%. The 1% miss rate, multiplied by billions of memory accesses per second, still matters, which is why CPU designers have steadily grown TLB sizes and added second-level TLBs over the past two decades. When the kernel switches between processes, it must flush parts of the TLB, since the new process has different page tables: one of the hidden costs of context switching.

Page faults: the productive kind

A page fault sounds like an error. Most are not: the everyday ones are how the kernel implements many of its most useful features. Faults fall into three rough categories:

A minor page fault happens when the page is in physical memory but isn't yet mapped into this process. Example: when a program first reads a page of a file the kernel has cached. The kernel just adds an entry to the page table and returns. Cost: microseconds.

A major page fault happens when the page is not in RAM and must be fetched from disk, typically because it was swapped out, or because the program is reading a memory-mapped file for the first time. The kernel issues a disk read, suspends the process, and resumes it when the data arrives. Cost: milliseconds. Roughly a thousand times slower than minor faults.

An invalid page fault happens when the access truly is illegal: writing to a read-only page, dereferencing a null pointer, executing data marked non-executable. The kernel sends the offending process a SIGSEGV signal, and unless the process catches it, the program dies with the famous "segmentation fault" message.

Fig 4.9 · A page fault, decision tree

Most page faults are not errors. The kernel asks two questions, and three accesses take the three exits: a cached page is mapped in microseconds, a first read of a mapped file waits milliseconds for the disk, and a write through NULL ends in SIGSEGV.

How it works
  1. Minor. The data is already in RAM (a page another process has loaded, the page cache, or a fresh zero-filled page), so the kernel only writes the page-table entry.
  2. Major. The kernel starts the disk read, runs other processes while it waits, then maps the page and resumes: about a thousand times slower than a minor fault.
  3. Invalid. The address is unmapped or the access breaks the mapping's permissions; unless the process catches SIGSEGV, it dies with "segmentation fault".

Two beautiful uses of page faults

Memory-mapped files. When you call mmap() on a file, the kernel doesn't read the file. It sets up page table entries marking the relevant virtual addresses as backed by that file, but invalid (not yet present). The first time you touch a page, you take a page fault, and the kernel reads just that one page from disk. Reading a 100 GB file as if it were a contiguous array in memory becomes trivial, because only the pages you touch are loaded. This is how databases and search engines handle large data, and how every shared library loads on Linux.

Copy-on-write fork. When a UNIX process calls fork() to create a child process, the child receives a copy of the parent's entire address space. Naively, this would require duplicating gigabytes of memory. It doesn't. The kernel marks all of the parent's pages as read-only and shares them with the child. Only when one of them tries to write does a page fault occur, and the kernel makes a private copy at that moment. Most pages are never written; most fork-and-exec sequences (the standard way to launch a new program on UNIX) never copy any pages at all. The cheapest way to make a copy is to lie about having made it.

Fig 4.10 · Fork, then write: when shared pages diverge

After fork() the two page tables point at the same pages, all read-only, and nothing is copied. When the child writes page B, the fault makes the kernel copy that one page and give the child its own; A and C stay shared.

How it works
  1. The trap. Marking shared pages read-only turns the first write into a page fault, so the kernel learns exactly which page needs copying, when.
  2. The parent's side. If the parent writes B later, the kernel sees that nobody else maps it any more and simply makes it writable again, without a copy.
  3. Fork, then exec. A child that calls execve() straight away replaces its address space before writing anything, so launching a program copies almost no pages.

Dirty COW (CVE-2016-5195). A bug in Linux's copy-on-write logic, present in the kernel for nine years before being discovered, allowed an unprivileged attacker to write to read-only files, including /etc/passwd, by exploiting a race condition between the page fault handler and the kernel's COW machinery. Privilege escalation followed trivially. Much of operating system security depends on subtle correctness in subsystems most users will never see.

Fig 4.11 · Dirty COW: the race that broke Linux

Dirty COW exploited a race in the COW path. A thread tries to write a read-only file mapping, taking a page fault. The kernel begins COW: it allocates a copy and is about to install it as read-write in the writer's page table. Between "allocate copy" and "install copy in page table" there is a brief window. A second thread, on the same process, calls madvise(MADV_DONTNEED) on the same page, which legally discards the COW mapping. The first thread resumes, retries the write, but now the page table no longer has the copy installed, so the write goes through to the original mapping: the read-only file. An unprivileged process can therefore write to any file it can read. /etc/passwd is world-readable. Local privilege escalation in 60 lines of C. The bug had been in the kernel since 2007. Phil Oester reported it after seeing it abused on a production system; Linus Torvalds patched it within hours; every Linux distribution shipped fixes within days.

04 · Filesystems

A tree of names on a flat array of blocks

A disk, at its lowest level, is a flat array of fixed-size blocks. A spinning hard drive presents itself to the OS as billions of 512-byte sectors numbered 0, 1, 2, … An SSD presents the same abstraction over a radically different physical reality. From this raw substrate, the filesystem builds the structure you actually use: files with names, organised into directories, organised into a tree, with metadata about ownership and permissions and timestamps. None of this structure exists at the hardware level. It exists because the filesystem code pretends it does.

The inode: where a file actually lives

In UNIX-derived filesystems (which is most of them), the central data structure is the inode, short for "index node." Every file has exactly one inode, and the inode contains everything about the file except its name and its data:

Notice what's not there: the filename. In UNIX, a filename is a property of the directory it lives in, not the file. A directory is itself a special kind of file whose contents are a list of (name, inode-number) pairs. To open /home/yki/notes.txt, the kernel looks up the inode for /, reads its directory contents to find the entry for home, follows that to the next directory's inode, and so on, until it reaches notes.txt's inode. Then it uses the inode's block list to read the actual data.

Because the name lives in the directory, a single file can have several names: multiple directory entries pointing to the same inode, called hard links. The file is only deleted when its link count drops to zero. For the same reason, renaming a huge file is instant: only the directory entry changes. The inode and its data don't move.

Fig 4.12 · Filename → inode → data blocks

The name lives in the directory and the file lives in the inode: notes.txt and backup.txt hold the same inode number, so they are one file with two names. The inode lists the file's blocks, which can sit far apart on the disk.

How it works
  1. Lookup. Opening /home/yki/notes.txt reads one directory per path component, from / down, until the last name gives the inode number.
  2. Hard links. The link count says how many names point at the inode. Deleting a name lowers it; the data is freed only when it reaches zero.
  3. Runs of blocks. Modern filesystems (ext4, XFS, APFS) record runs such as 102–104 instead of every block number, and try to keep a file's blocks together.

The everything-is-a-file principle

UNIX took the inode concept beyond regular files. Every kernel-managed resource is exposed as a file:

  • Your keyboard is /dev/input/event0.
  • Random numbers come from /dev/urandom.
  • The state of every running process lives under /proc/<pid>.
  • Network connections are accessed through file descriptors with read and write.
  • Hardware sensors expose temperature and voltage as files in /sys.

The same four system calls work on all of them: open, read, write, and close (a socket arrives through a different door, but once you hold its descriptor it is read and write like everything else). This uniformity is one of the reasons UNIX-derived systems became so dominant: tools written for files work unchanged on devices, network connections, and process state. The shell pipeline that counts lines in a text file (cat file | wc -l) counts them just as well in the output of a sensor driver or a debugging tool.

Journaling: the database technique that saved filesystems

A filesystem that simply writes data and metadata to disk wherever convenient has a fatal weakness: power loss. If the machine crashes between writing data and updating its corresponding metadata (or vice versa), the filesystem becomes inconsistent: files exist whose blocks are still listed as free, or directory entries point at non-existent inodes. The classic UNIX response was fsck, a program that scans the entire disk after a crash to find and fix inconsistencies. On a multi-terabyte disk this could take hours.

The modern solution, borrowed from database theory, is the journal, a small, dedicated region of the disk where every intended modification is written first, then applied to the main filesystem. After a crash, the kernel only has to replay the journal from where it left off, applying or discarding incomplete operations. Recovery takes seconds instead of hours. ext4 (Linux), NTFS (Windows), and HFS+ (older macOS) all journal. The technique is called write-ahead logging; we'll meet it again in Chapter 13 when we get to databases.

Fig 4.13 · Journaling: write your intent before doing it

The change goes to the journal first, sealed by a commit record, and only then to its home in the filesystem. After a crash, boot replays every committed change and discards any without a commit, so the disk is consistent in seconds.

How it works
  1. The atomic step. The commit record is one small block, written after the rest of the entry has reached the disk. Whether it exists decides the outcome.
  2. What is logged. By default ext4 and NTFS journal metadata only (inodes, bitmaps, directories); ext4's data=journal mode also logs file contents, writing them twice.
  3. The lineage. This is write-ahead logging, taken from databases (Chapter 13). Before journals, fsck had to scan the whole disk after a crash, which took hours.

The newest generation goes further: copy-on-write filesystems like ZFS, btrfs, and Apple's APFS never overwrite existing data. Every modification writes new blocks; only after the write succeeds is the metadata updated to point to them. The old version remains until garbage-collected, which gives you essentially-free snapshots, atomic operations on entire directories, and built-in checksumming to detect silent disk corruption.

Fig 4.14 · Copy-on-write filesystem: never overwrite, just re-point

A copy-on-write filesystem never overwrites a block: changing 103 writes a new 103′, a new parent and a new root, and one pointer switch makes the change live. The old root still describes the old file, so a snapshot costs nothing until the versions diverge.

How it works
  1. Crash safety. Before the switch the old tree is whole; after it the new one is. A crash before the switch loses only the change, never the filesystem.
  2. Checksums. Every block can carry a checksum checked on each read, so silent disk corruption is caught. ZFS and btrfs cover data too; APFS covers metadata.
  3. The cost. One changed byte rewrites a block at every level up to the root: write amplification. NetApp's WAFL made this trade in the early 1990s; ZFS, btrfs and APFS make it now.
05 · IPC

How processes talk

Processes are isolated by design: virtual memory and privilege separation exist so that one process cannot read or modify another's memory. But isolation taken to its extreme produces a useless system: programs that share nothing cannot compose into pipelines, cannot coordinate, cannot even tell each other when work is done. The kernel therefore exposes a controlled set of mechanisms for processes to communicate, collectively called inter-process communication, or IPC.

Each IPC mechanism is a different point on the trade-off between convenience, performance, and flexibility.

The pipe: UNIX's most beautiful idea

The pipe reached UNIX in 1973. Doug McIlroy had been urging the idea for years, and Ken Thompson finally built it in an evening. A pipe is a kernel-allocated ring buffer with two file descriptors attached: one process writes to one end, another reads from the other. The kernel handles flow control: if the buffer is full, the writer blocks; if it is empty, the reader blocks. No shared memory. No locks. No protocol. Just a stream of bytes.

Fig 4.15 · A pipe is a kernel ring buffer with two ends

A pipe is a ring buffer in the kernel with a write end and a read end. When the ring is full the writer blocks until the reader frees space, and when it is empty the reader blocks until bytes arrive: flow control with no locks in either program.

How it works
  1. Two descriptors. pipe() returns one file descriptor for each end; the shell wires the writer's standard output to one and the reader's standard input to the other.
  2. The size. A Linux pipe holds 64 KB by default, so a fast writer runs ahead of a slow reader by at most that much.
  3. The lineage. Doug McIlroy pressed for pipes for years; Ken Thompson added them to UNIX in 1973, and every shell pipeline since runs on this mechanism.

In the shell, a pipe is written as a single character:

shell 
# Count how many unique lines start with "ERROR" in a log:
cat server.log | grep "^ERROR" | sort | uniq | wc -l

# Five separate processes, each doing one small thing.
# The shell creates pipes between them. Output of one
# becomes input of the next, streamed byte-by-byte.

Each program knows nothing about the others: it reads standard input and writes to standard output as if they were ordinary files, and the kernel arranges those file descriptors to be the ends of pipes. All five run in parallel; the output of one streams into the next as fast as either can handle it. That is one reason UNIX produced a culture of small composable tools rather than monolithic applications.

Fig 4.16 · The UNIX philosophy, in five processes

Five small programs joined by four pipes run at once, each reading standard input and writing standard output with no idea what is on the other end. Lines stream through as they arrive, except at sort, which must see the last line before it can print the first.

How it works
  1. The wiring. The shell calls pipe() four times and fork() five, then points each program's standard output at the next one's standard input.
  2. Streaming. grep and uniq work a line at a time; sort and wc must reach the end of their input before they can answer.
  3. The philosophy. Doug McIlroy's summary: write programs that do one thing well, and write them to work together.

"This is the Unix philosophy: write programs that do one thing and do it well. Write programs to work together. Write programs to handle text streams, because that is a universal interface."

Doug McIlroy, inventor of the UNIX pipe

Signals: a doorbell to a process

Pipes carry data. Signals carry no data, only the bare fact that something happened. A signal is a small, numbered notification delivered asynchronously to a process: number 2 (SIGINT) is what the kernel sends when you press Ctrl+C; number 9 (SIGKILL) is "stop now"; number 15 (SIGTERM) is the polite "please stop." A process can handle most signals (it registers a function; on arrival the kernel hijacks the process, runs the handler, then resumes), ignore them, or take the default action. Two signals, SIGKILL and SIGSTOP, can be neither handled nor ignored: the first always kills, the second always suspends.

Fig 4.17 · A signal arrives mid-execution

Ctrl+C makes the kernel mark SIGINT pending; the program runs on until its next return from the kernel, where it is diverted into its handler and then resumed where it stopped. SIGKILL never reaches the program: the kernel ends the process without running any of its code.

How it works
  1. Three reactions. A process can handle a signal with its own function, ignore it, or take the default action: terminate, stop, or nothing.
  2. Uncatchable. SIGKILL and SIGSTOP can be neither handled nor ignored, so an administrator can always stop a process that has trapped everything else.
  3. Crude by design. A signal is just a number. A second signal of the same kind arriving while the first is still pending merges with it.

Shared memory and semaphores: the no-copy IPC

Pipes and signals are convenient. They are not fast. Every byte through a pipe is copied: from the writer's userspace into the kernel buffer, then out of the kernel buffer into the reader's userspace. For high-throughput communication (gigabytes per second between two processes on the same machine), shared memory is the only viable mechanism. Two processes call into the kernel to map the same physical pages into both their virtual address spaces. After that, the shared region is ordinary memory, no slower than any other: no copy, and no kernel involvement on each access.

The cost of zero-copy is a classic concurrency problem: two processes touching the same memory must coordinate so that neither sees the other mid-update. The kernel exposes semaphores for this: counters that processes increment and decrement atomically, used as gates. A semaphore initialised to 1 acts as a mutex (one process at a time may pass). Initialised to N, it acts as a resource pool. The mathematics is Edsger Dijkstra's from 1965, formalised in his note "Cooperating Sequential Processes," and underlies every modern concurrent system.

Fig 4.18 · Two processes, one region, one gate

Both processes map the same physical page at different virtual addresses, so what one stores the other can load, with no copy and no system call. A semaphore holding 1 lets one in at a time: A takes the 1, B finds 0 and sleeps, and A's sem_post() wakes it.

How it works
  1. The mapping. shm_open() and mmap() put the same physical pages into both address spaces; after that the region is ordinary memory.
  2. The fast path. On Linux, sem_wait() and sem_post() are atomic instructions on a counter in shared memory; the kernel is called only when someone must sleep or be woken.
  3. Counting. A semaphore started at N admits N at once, a pool rather than a lock. The idea is Dijkstra's, from 1965.

Sockets: when the other process is on another machine

A socket is a generalisation of the pipe. Instead of a kernel-managed pipe to a process on the same machine, you communicate over a connection, either to another local process (a "UNIX domain socket") or to a process on a different machine entirely (a "network socket," using TCP or UDP). The same system calls apply: read, write, and close. From the application's perspective, the network is just another file. The kernel, the network drivers, the protocol stack, and the wire are all hidden beneath the same few calls.

That is why a web browser, a database client, and an SSH session all use roughly the same code shape: open a socket, write a request, read a reply, close. Part III opens up what happens between write and read: ARPANET, packet switching, TCP, DNS, TLS, HTTP. Until then, the kernel makes it look like a file. That, more than anything else, is the kernel's job.

06 · Security

When the kernel breaks

Everything we've built in this chapter (the privilege boundary, the address-space isolation, the file permission checks, the IPC mediation) rests on one assumption: the kernel is correct. A bug in the kernel is therefore not an ordinary bug. A user-space program with a buffer overflow can be exploited to take over that program. A kernel with the same kind of bug can be exploited to take over everything: the kernel itself, every other process, every file, every keystroke.

Privilege escalation, more carefully

A privilege escalation attack is one where a process gains more privilege than it was supposed to have. The two important versions:

Vertical escalation: moving up the privilege ladder. A normal user process exploits a bug to become root, or root exploits a bug to enter Ring 0 (kernel mode).

Horizontal escalation: moving sideways at the same privilege level into another process's data. Reading another user's files, hijacking another user's session.

Kernel privilege-escalation bugs of the last decade include Dirty COW (the copy-on-write race condition mentioned earlier, 2016), DirtyPipe (a flaw in pipe-buffer initialisation that allowed writes to read-only files, 2022), and dozens of bugs in device drivers. Driver code is vast, often less audited than the core kernel, and runs in Ring 0. Most modern kernel exploits chain together multiple bugs: an information leak (to defeat KASLR, the kernel's version of ASLR), then a memory-corruption primitive (to overwrite something useful), then a privilege escalation.

Containers: not virtual machines

Containers, the units Docker and Kubernetes run, are often described as "lightweight VMs," which is misleading. A virtual machine emulates an entire computer (its own kernel, its own everything) on top of a hypervisor. A container is a normal Linux process that runs on the one shared kernel: a process the kernel has lied to, using two Linux features:

Namespaces partition kernel resources so that different processes see different views. There are namespaces for process IDs (a containerised process believes it is PID 1, even though to the host it might be PID 8472), for the network (the container has its own virtual network interface), for mounts (its own root filesystem), for user IDs, for hostnames, and more. Inside its namespaces, the container looks like a complete isolated system.

Cgroups (control groups) limit how much of each resource a process group can use: CPU time, memory, disk I/O, network bandwidth. Together with namespaces, this gives Docker its model: cheap, fast isolation that doesn't require a hypervisor.

Fig 4.19 · VMs vs containers

A virtual machine runs its own guest kernel on a hypervisor; a container is an ordinary process whose system calls go to the one host kernel, fenced by namespaces (what it can see) and cgroups (what it can use). That shared kernel is why containers are light, and why one kernel bug can reach every container on the host.

How it works
  1. Hypervisors. KVM turns Linux into one; VMware ESXi, Xen and Hyper-V are others. CPU extensions (Intel VT-x, AMD-V) let guest kernels run directly on the processor.
  2. The fences. Namespaces and cgroups are ordinary kernel features; the next two figures show each.
  3. The middle ground. MicroVMs such as AWS Firecracker boot a minimal guest kernel in about 125 ms, giving each container its own kernel at nearly container cost.

VMs isolate kernels, so a compromise of one guest doesn't affect others. Containers share a kernel, so a kernel privilege-escalation bug can let a malicious container take over the host and every sibling container. Cloud providers running multi-tenant workloads typically use VMs, or containers wrapped in micro-VMs (AWS's Firecracker exists for exactly this). Single-tenant deployments use plain containers because they're far cheaper.

Fig 4.20 · Namespaces: each container sees its own world

Ask the same five questions from inside container A, inside B and on the host, and one kernel gives three sets of answers: each container sees its own PID 1, hostname, network and root filesystem. Namespaces are translation tables, not copies: to the host, A's PID 1 is just process 8472.

How it works
  1. Eight kinds. Mount, UTS (hostname), IPC, PID, network, user, cgroup and, since Linux 5.6, time. Each can be set separately.
  2. Making one. clone() or unshare() with a flag such as CLONE_NEWPID puts a process in a fresh namespace; its children inherit it.
  3. The wiring. A container's eth0 is one end of a virtual Ethernet pair; the other end sits on the host, which routes between them.
Fig 4.21 · Cgroups: quotas as taps on the resource flow

Namespaces decide what a process can see; cgroups decide what it can use, with a CPU and a memory limit per group that the kernel enforces. A runaway batch job wanting 12 CPUs is held to its 4, and when it outgrows its 16 GB the kernel kills it, while web and db never notice.

How it works
  1. The interface. Cgroup v2 is a filesystem at /sys/fs/cgroup. Writing 400000 100000 to cpu.max allows 4 CPUs' worth of time in every 100 ms period.
  2. Memory. Past memory.max the kernel first reclaims the group's own pages; if that fails, the OOM killer picks a process inside the group.
  3. Who writes them. Docker's --cpus and --memory, Kubernetes resource limits and systemd's services all set these files, as do io.max and pids.max for disk and process counts.

eBPF: safe code inside the kernel

A more recent Linux feature is eBPF, "extended Berkeley Packet Filter." It allows user programs to upload small pieces of code into the running kernel, where they are attached to specific events (network packets, system calls, function entries) and run inside Ring 0.

The obvious worry is that this lets user code into the kernel, historically the worst possible security outcome. eBPF answers with a verifier: a static analyser in the kernel that examines every uploaded program and refuses to load it unless it can prove the program will always terminate, never read out-of-bounds memory, and never crash. Programs that pass the verifier are then JIT-compiled to native machine code and run essentially as fast as compiled kernel code. (Belt and braces: modern kernels also restrict who may load programs at all.)

Fig 4.22 · eBPF: untrusted code in the kernel, made safe by proof

Before an eBPF program may run in the kernel, the verifier must prove that it ends and never reads outside its bounds: a packet counter passes, is compiled to native code and runs on every packet. A loop the verifier cannot bound is refused with an error, so it never runs at all.

How it works
  1. The toolchain. clang compiles restricted C to eBPF bytecode, and the bpf() system call hands it to the kernel.
  2. The proof. The verifier walks every path through the program, tracking the range of every register. Loops pass only when it can bound them (allowed since Linux 5.3), and its effort is capped.
  3. A second guard. Most systems also let only privileged users load programs, so the verifier is not the only line of defence.

eBPF has become the foundation of modern Linux observability and networking: tools like Cilium (high-performance network policy), bpftrace (kernel tracing), and Falco (runtime security monitoring) all build on it. The pattern generalises. Untrusted code runs inside a privileged context under machine-enforced constraints: proved harmless up front in eBPF's case, fenced in at runtime when the browser runs untrusted JavaScript in Chapter 12.

The question every layer answers. What is less-trusted code allowed to do here, and what stops it? Every mechanism in this chapter (the kernel itself, the privilege boundary, virtual memory, filesystem permissions, container isolation, eBPF verification) is a different answer to that one question, and each restricts rather than trusts. Operating system security is the discipline of building such mechanisms and then living with the fact that any one of them can have a bug. The kernel is not a fortress. It is layers of walls, and the guards themselves have to be checked by other guards. There is no bottom, only better and worse layers.

What you now understand

The kernel is a program that owns the hardware and mediates everything every other program does. Written in C and loaded by a bootloader, it runs forever in Ring 0. It comes in two main shapes: monolithic (everything in Ring 0, fast, fragile) and microkernel (minimal Ring 0, message-passing, safer and slower), with most real systems sitting somewhere on that spectrum. Its scheduler, anchored mathematically in queueing theory, decides which process gets the CPU at each microsecond. Linux's CFS, and EEVDF after it, does this in O(log N) using a red-black tree of virtual runtimes. Its virtual memory subsystem maintains a four-level page table per process, accelerated by a translation cache (TLB), and uses page faults productively to implement memory-mapped files and copy-on-write fork. Its filesystem turns a flat array of disk blocks into a tree of inodes and names, made crash-safe by journaling or copy-on-write. Its IPC mechanisms (pipes, signals, shared memory, sockets) are the controlled boundary across which isolated processes can still cooperate. And its security depends entirely on its own correctness, which is why kernel bugs are so dangerous, and why each new mechanism (containers, eBPF) is layered behind further verification.

With this, the kernel is in view from both sides. The Bridge at the close of Part I showed it as silicon: privilege rings as a CPU bit, the trap as a wire-level mechanism, the MMU as a hardware unit, the timer as the single piece of hardware that makes preemption possible. This chapter showed it as code. Same object, two different perspectives, and the kernel becomes legible only when both are visible at once: thirty million lines of C running in Ring 0, sustained by a hardware contract that lets it own the machine.

The next chapter climbs out of the kernel and into the language it was written in. C (Ritchie at Bell Labs, 1972) is still the language of every production kernel. Pointers turn out to be the addresses we just walked through: the source of C's power, and of every memory bug we met in Chapter 3.

01 · The portability problem

One source. A thousand binaries.

Until 1973, an operating system was a thing you wrote in assembly for one specific machine. To run that OS on a different computer, you didn't recompile. You rewrote it, instruction by instruction, for that computer's CPU. Then C arrived, and one source file became a thousand binaries.

In 1965, IBM shipped the System/360. To write software for it, you wrote System/360 assembly directly, in mnemonics like L, ST, BAL, encoded in EBCDIC. When DEC shipped the PDP-11 in 1970, the machine spoke an entirely different assembly language. A program for the System/360 was unusable on the PDP-11. Not "needs porting." Unusable. The bits did not even mean the same opcodes.

This was the normal state of computing: operating systems, compilers, every piece of systems software, all rewritten per machine. A small army of programmers spent their careers translating known-good programs into yet another assembly. When a new CPU appeared, porting cost so much that most software simply did not make the trip. Each generation of hardware was an island.

Fig 5.1 · One C source, many targets

One C function compiled for three processors: different instructions, different registers (eax, w0, a0) and different encodings, x86's variable-length bytes against the fixed 4-byte words of ARM and RISC-V. The behaviour is identical, which is what portable means for C: not one binary everywhere, but one source that compiles to each.

How it works
  1. Calling conventions. Each platform's ABI says where arguments arrive (edi/esi, w0/w1, a0/a1) and where the result goes back.
  2. The lea trick. x86 compilers borrow lea, an address-arithmetic instruction, to add two registers into a third in one step.
  3. The w in addw. On 64-bit RISC-V it adds 32-bit ints. With the compressed extension both instructions shrink to 2 bytes each.

What makes a language portable

Three things. First, the language must abstract away CPU-specific details (register sets, instruction widths, calling conventions) without forcing the programmer to give up speed. Second, it must be small enough that a small team can write a compiler for a new architecture. Third, its memory model must be loose enough to map cleanly onto whatever memory hardware provides: bytes here, words there, alignment requirements everywhere.

C achieves all three with one trade. Its types map directly onto machine words. Its control flow maps directly onto conditional jumps. Its data structures are layouts you could draw on graph paper. The cost: you, the programmer, see the metal whether you want to or not. The benefit: a competent compiler-writer can target a new ISA in a few months, and C written for the PDP-11 half a century ago still compiles on a 2026 ARM Mac. The dialect has aged, but the language has never broken its old programs lightly.

BCPL → B → C

BCPL (Martin Richards, Cambridge, 1967) was a typeless language designed for writing compilers. Words. No types. Just memory. B (Ken Thompson at Bell Labs, 1969) was a smaller, cleaner BCPL: also typeless, also word-oriented. B ran on early UNIX. But the PDP-11 that arrived at Bell Labs in 1970 was byte-addressable, and B's word-only model fit it badly. In 1972 Ritchie added types (int, char, pointers, structs) and called the result C. The name was exactly the joke it looks like: the language that comes after B.

C did not solve portability by being abstract. It solved it by being just barely abstract enough: close enough to assembly to compile efficiently on any reasonable CPU, just far enough above it to never mention specific registers.

02 · Ritchie and Thompson at Bell Labs

Two men, a discarded minicomputer, four years.

In a windowless room at Bell Labs in 1969, Ken Thompson found a discarded PDP-7 and started writing a programming environment for himself. His friend Dennis Ritchie joined. Within four years they had built UNIX, written the C language to write more UNIX in, and laid the foundations of every operating system you use today. No marketing. No grand plan.

The story begins with a project that failed. Bell Labs had been one of three institutions building Multics, a vast time-sharing operating system meant to be a "computing utility" for hundreds of simultaneous users. Multics was technically remarkable and managerially catastrophic. By 1969 Bell Labs had pulled out. Thompson and Ritchie, who had been Multics contributors, were left with the appetite for that kind of system but no machine, no team, and no permission.

Thompson salvaged an unused PDP-7, an 18-bit minicomputer already old by 1969; DEC had stopped selling it. He started writing a small operating system for it, partly to play a space-travel game he had ported from Multics, partly to have an environment to work in. By the end of 1969 there was a kernel, a shell, an editor, and a primitive filesystem. Brian Kernighan, noting that the system was a stripped-down Multics, quipped that they should call it "UNICS" (UNiplexed Information and Computing Service), a pun on Multics. The name became UNIX.

Fig 5.2 · UNIX's rewrite, in time

UNIX began in 1969 as PDP-7 assembly and moved to the PDP-11 still in assembly; in 1973, with C ready, Ritchie and Thompson rewrote the kernel in it. Four years later it ran on an Interdata 8/32, a machine of a different design, carried over largely by recompiling.

How it works
  1. Why C. B had one type, the machine word. The PDP-11 addressed bytes, so the language needed types; Ritchie added them, and structs, to make C.
  2. The rewrite. The 1973 Fourth Edition was the first UNIX with its kernel mostly in C; a small machine-dependent part stayed in assembly.
  3. The book. Kernighan and Ritchie's The C Programming Language (1978) served as the language's definition until the ANSI standard of 1989.

The PDP-11

The PDP-11 was a 16-bit minicomputer that DEC sold from 1970 onwards. It was small (the size of a refrigerator, not a room), had eight general-purpose registers, used byte-addressable memory, supported indirect addressing through registers, and had a clean, regular instruction set. C's design choices are PDP-11 idioms made into a language: pointer arithmetic that adds sizeof(*p) bytes, structures laid out in memory in declaration order, the equivalence of arrays and pointers. To a first approximation, C is a portable PDP-11 assembler.

K&R, 1978

Brian Kernighan and Dennis Ritchie published The C Programming Language with Prentice-Hall in 1978. Two hundred and twenty-eight pages. Every example a few lines, compilable, runnable. The famous opener, a program that prints hello, world, is on page 6. K&R defined the language until ANSI standardisation in 1989, and it is still on the bookshelf of every working C programmer. The book is unfussy, exact, and assumes intelligence: someone could plausibly read it in an afternoon and write working code that night.

"C is quirky, flawed, and an enormous success."

Dennis Ritchie
Fig 5.3 · PDP-7 to PDP-11 · the machines that shaped C

On the PDP-7 an address named a whole 18-bit word, two characters at a time; on the PDP-11 every byte had its own address. A pointer to a character must then step by 1 and a pointer to an integer by 2, which is why C, unlike B, gave its pointers types.

How it works
  1. The PDP-7. Bell Labs' machine had 8K words of 18 bits. B, its language, had a single type, the word; reaching one character meant shifting and masking.
  2. The PDP-11. A 16-bit design with byte addresses, eight registers and regular addressing modes. Its bytes are what forced types into the language.
  3. The legacy. Flat byte-addressed memory and pointers that scale by the size of what they point at are C's model, and nearly every processor since provides it.
03 · Pointers as math

A pointer is an integer with attitude.

A pointer is not a mysterious thing. It is an integer: the address of a byte in memory. What makes C feel different from every language since is that it lets you do arithmetic on these integers directly, without a safety net, and trusts you to know what you're doing.

To a C program, memory is a giant array of bytes, and each byte has an integer address. On a 64-bit machine, those addresses run from 0x0000_0000_0000_0000 to 0xFFFF_FFFF_FFFF_FFFF, more addresses than any single machine will ever fill. A pointer in C is just one of those integer addresses, stored in a variable that the compiler has labelled with the type of thing the address is supposed to point at.

Three operators do nearly all the work. The unary & takes the address of a variable: &x is "the address where x lives." The unary * dereferences a pointer: if p is the address of an int, then *p is the int stored there. And pointer arithmetic (p + 1) does not mean "the next byte." It means "the next thing of the type p points to." If p is an int * on a 32-bit-int machine, p + 1 advances four bytes. The compiler scales the arithmetic for you. This is the entire trick.

Fig 5.4 · A pointer walks down memory

Three pointers start at 0x100 and take the same step, ++: the char pointer moves 1 byte, the int pointer 4, the double pointer 8. The compiler scales pointer arithmetic by the size of the type, so p + 1 always means the next element, never the next byte.

How it works
  1. The sizes. A char is 1 byte by definition; int is 4 and double 8 on today's common machines, though the standard only sets minimums.
  2. What *p reads. The bracket under each pointer is the span a dereference loads: one, four or eight bytes from its address.
  3. Where it leads. Strings are char pointers walking to a zero byte, and arrays are the same arithmetic in disguise, as the next figure shows.

Arrays are pointers in disguise

The expression a[i], where a is an array, is defined by the C standard to be exactly equivalent to *(a + i). Not "compiles to similar code": defined to be equivalent. The array indexing operator is syntactic sugar for pointer arithmetic, and it works in both directions. With a pointer p, p[3] is a legal C expression meaning *(p + 3); with an array a, *a is a[0].

Fig 5.5 · a[i] ≡ *(a + i)

The C standard defines a[i] as *(a + i): add i elements to the address, then read what is there. Because addition commutes, 2[a] is the same expression and reads the same 99; arrays in C are a notation over pointer arithmetic.

How it works
  1. The rule. C99 §6.5.2.1: "E1[E2] is identical to (*((E1)+(E2)))."
  2. The decay. In most expressions an array's name turns into a pointer to its first element, which is why a + 2 means an address at all.
  3. The cost. Nothing in *(a + i) knows how long the array is, so a[10] on a six-element array reads whatever lies beyond it.

What this lets you do

Linked structures built by chasing pointers from one node to the next. Arrays of arrays, dynamically sized. Function pointers: pointers to executable code, the foundation of callbacks, interrupt handlers, and the virtual method tables (vtables) of Chapter 6. Type-punning casts that let you treat the same bytes as different types, useful for binary protocols and for reading raw hardware registers. Everything systems software does, eventually, comes down to this.

What this lets you screw up

A pointer that points outside its valid range will happily write anywhere your process is allowed to write. There is no check. arr[i] with i too large does not raise an exception; it stores into whatever lies 4×i bytes past the start of arr. If that is the saved return address on the stack, you have the buffer overflow of Chapter 3: the mechanism drawn on paper there is exactly this, a few lines of C compiled with bounds checking off (which is to say: compiled as C).

The trade: Pointer arithmetic gives you the most direct access to memory of any high-level language. It is also the source of approximately every memory-corruption vulnerability in computing history. The second is the price of the first.

04 · Manual memory management

You allocated it. You free it.

Every byte of dynamic memory your C program uses, you allocated. Every byte you allocated, you must free. Forget to free, and your program leaks until the OS kills it. Free twice, or use a freed pointer, and your program corrupts itself in ways that may not show up for hours. C makes you the bookkeeper. There is no garbage collector.

Recall from Chapter 3 that memory comes in two main flavours: the stack, which grows and shrinks automatically as functions enter and exit, and the heap, a region the kernel hands the process for long-lived allocations. Heap memory requires explicit requests. C exposes those requests through two functions: malloc(n) asks for n bytes of heap and returns the address; free(p) tells the allocator that the bytes at address p are no longer needed.

Behind these two functions lives an entire algorithm, the allocator. The kernel hands the process a single big chunk of address space (via the brk or mmap system calls). The allocator subdivides that chunk into smaller pieces in response to malloc calls, and stitches pieces back together when free calls return them. Over time, allocations and frees leave the heap a patchwork: free chunks of various sizes, threaded onto the allocator's free list, interleaved with allocated chunks, each tagged with whether it is in use.

Fig 5.6 · The heap, as a free list

After five allocations and two frees the heap holds 400 free bytes in three pieces, and a request for 300 fits none of them. That is fragmentation: free memory in pieces too small to use, so the allocator must ask the kernel for more.

How it works
  1. The list. Each free chunk stores, inside its own unused bytes, a pointer to the next free chunk; the allocator walks that list to find room.
  2. Coalescing. Freeing a chunk next to free space merges the two. Here every free piece is fenced by a chunk still in use, so nothing can merge.
  3. Strategies. First fit, best fit and size-class bins (glibc's ptmalloc, jemalloc) trade speed against fragmentation.

The two failure modes

There are exactly two ways to mishandle malloc and free. The first is to allocate and never free: a leak. The chunk stays in use forever, even though no pointer in the program references it any more. Run a leaky program long enough and the OS kills it for exhausting memory. The second is the inverse: free a chunk and keep using the pointer to it. This is a use-after-free. The chunk has gone back to the free list and may have been handed to a different malloc caller; reading it now reads someone else's data, writing it corrupts that data.

Fig 5.7 · Leak vs use-after-free

A leak is silent and slow: memory accumulates until the OS kills the process. A use-after-free is silent and fast: the moment free returns, the chunk is back on the allocator's free list, and a future malloc may hand it to a totally different part of your program. Reads from the dangling pointer return whatever that other code has stored. Writes corrupt it. In a security context, the attacker arranges for a sensitive object (a function pointer, a credentials structure) to be allocated where the dangling pointer still points, then writes through the dangling pointer to take control. UAF is the modern equivalent of the buffer overflow.

Why this is still in production

Garbage collection was invented in 1959 by John McCarthy for Lisp. By 1990 it was well-understood. C kept refusing it for one reason: predictability. A garbage collector decides on its own schedule when to pause your program and walk the heap. For an audio stack draining 48,000 samples per second through a buffer a few milliseconds deep, a 100-millisecond GC pause is catastrophic. C's manual model gives you a contract: memory is freed exactly when you free it, never sooner, never later. The price is that you must be right.

05 · Undefined behavior

The optimiser's cruel logic.

The C standard contains a list of operations whose behavior is "undefined." This does not mean they crash, or fail, or return garbage. It means the standard places no requirement at all on what happens. Modern optimisers will exploit that freedom in ways that look like betrayal. Code that worked for ten years can break catastrophically on the next compiler upgrade.

The core of the list is short and dangerous: signed integer overflow; dereferencing a null pointer; reading or writing past the end of an array; using a value before initialising it; modifying a string literal; data races between threads. Each is a contract the programmer has implicitly accepted: "I promise I will never do this." The compiler takes that promise on trust, never checking whether you can keep it, and generates code that only makes sense if you did.

The canonical example is a function that checks for signed integer overflow before doing something dangerous:

Signed overflow is undefined behaviour, so the compiler may assume it never happens; from that, i + 1 < i is always false and the check is dead code. At -O2 gcc deletes it, leaving only an add and a return.

How it works
  1. The safe test. Check before adding, if (i == INT_MAX), or use __builtin_add_overflow in gcc and clang.
  2. The kernel's answer. Linux builds with -fno-strict-overflow and -fno-delete-null-pointer-checks, switching these deductions off.
  3. Not malice. The standard lets the optimiser assume undefined behaviour never occurs; the same freedom is what lets it delete code that truly is dead.

NULL dereference

A pointer with the value 0 (or NULL, the macro that means the same thing) is conventionally "the address that points nowhere." The kernel arranges for the very first page of every process's virtual address space to be unmapped. Touching that page raises a hardware fault. The kernel intercepts the fault and converts it into a signal called SIGSEGV ("segmentation violation"), which by default kills the process. This is the Segmentation fault (core dumped) message that has greeted C programmers for fifty years.

Fig 5.9 · A NULL dereference, traced

A write through a NULL pointer crosses every layer: the MMU finds no mapping for address 0 and faults, and the kernel, finding the address in no region the process owns, sends SIGSEGV. The default action for that signal ends the process, which the shell reports as a segmentation fault.

How it works
  1. Why address 0 faults. Operating systems leave the lowest pages unmapped on purpose (Linux's mmap_min_addr), so a NULL access always traps.
  2. The same path. This is the "invalid" exit of the page-fault tree in Fig 4.9; only the outcome differs from a minor fault.
  3. The core file. "Core dumped" appears only when the system allows it; the dump is a snapshot of memory for a debugger to open.

The optimiser's contract, the programmer's homework

"Trust the programmer" was C's original philosophy and is still its operating stance. Modern optimisers take it to its logical limit, removing code based on assumptions you never knowingly made. The Linux kernel has accumulated a handful of -f flags telling GCC not to exploit specific UB optimisations. Security-aware C codebases compile with UndefinedBehaviorSanitizer in development (the compiler inserting checks for exactly the assumptions its optimising self exploits) to catch the cases where the programmer's and the compiler's models of "what is allowed" have drifted apart.

The right way to think about UB: not "the program might crash" but "the program's behavior is no longer governed by the source you wrote." This is the cost of C's performance.

06 · Why C survives

Half a century later, still in the foundation.

Every five years, someone writes a clickbait piece announcing that C is dying. Every five years, more C runs in production than ever before. Linux is C. macOS XNU and Windows NT are mostly C. The Python interpreter is C. The browser rendering this page is C++, C's first child. The TLS library that secured your connection is C. C is so deep in the foundations that it has become invisible.

Three properties keep C in the floor of every system. Performance: C compiles to assembly with no runtime overhead; what you write is, very nearly, what runs. Predictability: every operation has a known, bounded cost; there is no garbage collector to pause your program on its own schedule, no JIT to recompile your hot loop in the middle of a frame. Ubiquity: every hardware vendor ships a C compiler before any other language, every embedded system speaks C, every kernel API is described in C.

Fig 5.10 · Where C still runs in 2026

Whatever a program is written in, its work soon runs in C: a Python program's request passes through the CPython interpreter, OpenSSL and SQLite, libc and the Linux kernel, all written in C. C holds the layers where cycles and predictability matter most, and pays for it in memory-safety bugs.

How it works
  1. Why it stays. No garbage collector, a simple calling convention every other language can call into, and a compiler for nearly every chip ever made.
  2. The price. Microsoft and Google's Chromium team have each reported that about 70% of their serious security bugs are memory-safety bugs.
  3. The successor. Rust has been accepted in the Linux kernel since 2022 and is entering Windows and Android, one layer at a time.
Fig 5.11 · The C family tree · half a century of descendants

Most major languages since 1972 grew out of C or were built as answers to it, in three waves: objects on top of C's speed, C's syntax on a managed runtime, and C's speed with memory safety. The braces, semicolons and for loops of much of today's code are C's.

How it works
  1. First wave. Objective-C is a strict superset of C, and C++ nearly one: both compile C code almost unchanged.
  2. Second wave. Java, C# and Kotlin run on virtual machines with garbage collection; Perl, JavaScript and PHP borrowed C's look for scripting.
  3. Third wave. Rust proves memory safety at compile time through ownership; Go and Swift manage memory for you; Zig keeps manual control with fewer traps.

01 · The complexity problem

The crisis that wasn't a crash.

The 1980s software crisis was not a single failure but a slow, systemic realisation. Codebases that had been small enough for one team to keep in their heads were now too large for any human to model. Beyond fifty thousand lines, C codebases became unmaintainable, not because the code was wrong, but because no one could tell when it was right.

Frederick Brooks had already named the disease. The Mythical Man-Month, 1975, observed that adding people to a late software project makes it later: complexity does not reduce by parallelism, because the cost of communication grows faster than the cost of work. By the late 1970s, Bell Labs and IBM were running projects with hundreds of programmers and millions of lines of code, and watching them fail. IBM's own OS/360, the very project Brooks was writing about, was the canonical case study; Multics, which Bell Labs had walked out of a decade earlier, was the one Bell Labs remembered.

The diagnosis was that C gave the programmer one tool for organising code: the function. Functions could group statements; nothing grouped functions. There was no language-level concept of module, no class, no interface. A header file was a list of declarations and a polite request that callers stick to it. A struct was a list of fields with no associated behaviour. If your subsystem had thirty types and three hundred functions, the language had nothing to say about which functions belonged to which types. You enforced it by convention, in comments, in code review.

Fig 6.1 · The 1980s software crisis, in one chart

Brooks's arithmetic: n parts that can each affect the others have n(n − 1)/2 possible interactions, so doubling the parts roughly quadruples what can go wrong between them. C had no way to wall parts off from one another, and the classes and access rules of C++ were the answer.

How it works
  1. The source. Fred Brooks, The Mythical Man-Month (1975), applied the count to people: each pair on a team needs a channel, so adding people to a late project makes it later.
  2. The same for code. When any function may touch any data, every new part can collide with every old one, and the pairs outgrow the parts.
  3. The wall. A class with private members lets the compiler refuse every touch that bypasses the interface, cutting the lines that may exist.

The fix needed two things. First, a way to bind data and code together, to say "these functions operate on this kind of thing, and only on this kind of thing." Second, a way to talk about relationships between kinds: a Circle is a Shape; a TextEditor has a Buffer; a Logger can be any object that exposes a log() method. None of this is hard to do in C, by convention. The point is to make the convention enforceable by the compiler, so the cost of breaking it is paid once, at build time, by the person who broke it, rather than once per bug report by everyone.

02 · Stroustrup at Bell Labs

Simula's children, raised on C.

Bjarne Stroustrup arrived at Bell Labs in 1979, not far down the corridor from Ritchie and Thompson. He had just finished a doctoral thesis on distributed systems whose simulator he had written in a language called Simula 67. He loved Simula's expressiveness and hated its speed. C, in the same building, was the inverse: fast and ugly. The question that organised the next forty years of his life: could he have both?

Simula 67 was designed in 1967 by Ole-Johan Dahl and Kristen Nygaard at the Norwegian Computing Center, expressly for simulating physical systems. It introduced the modern object-oriented vocabulary: the words class, object, virtual, and even this (referring to "the current object") all originate there, and so do the ideas of inheritance and virtual methods, though Simula spoke of subclasses and virtual procedures. By 1979 Simula was a niche academic language, but its ideas had spread: Smalltalk had built an entire dynamic system around them. Stroustrup took them the opposite way. He would graft them onto C, imposing no runtime overhead unless you used them. This zero-cost philosophy became the language's defining trait.

The first version, in 1979, was "C with Classes," implemented as a preprocessor that translated the new constructs back to plain C. In 1983 the language was renamed C++, a pun on C's increment operator, ++, meaning "C, but more." In 1985 Stroustrup wrote the language's first book, and that year's release shipped as a true compiler. In 1989 ANSI convened a standards committee; the standard itself, C++98, took nine more years. By 2000 it was the dominant language for systems where C alone could not scale: trading platforms, telecommunications switches, browser engines, game runtimes.

Fig 6.2 · C++, in time

From Simula's classes to C++23: Stroustrup's C with Classes (1979) became C++, standardised in 1998. C++11 is the pivot, adding move semantics, lambdas, auto and smart pointers, and every standard since has added more while keeping almost all older code compiling.

How it works
  1. The aim. Stroustrup (1993): "C++ was designed to provide Simula's facilities for program organization together with C's efficiency and flexibility for systems programming."
  2. Early compilers. C with Classes and Cfront, the first C++ compiler, translated programs into C, so C++ could run wherever a C compiler did.
  3. The rhythm. Since 2011 a new standard has arrived every three years: 14, 17, 20, 23.

What Stroustrup built was a deal: you may add abstraction without losing speed. Classes compile to structs with associated functions, at no overhead. Inheritance with virtual methods compiles to a struct containing one extra pointer and an indirect call: the cheapest possible version of dynamic dispatch. Templates compile, per-instantiation, to type-specialised assembly. None of this is magic: it is C with the bookkeeping pushed up into the type system, where the compiler can check it and inline it away.

03 · Classes, inheritance, and the vtable

What "OO" looks like in memory.

A class is a struct with associated functions. A virtual method is a function pointer the compiler manages for you. Inheritance is one struct embedded inside another. Polymorphism is dereferencing one of those function pointers at runtime. Each is a layout in memory, and you can draw every one of them on graph paper.

Start with a non-virtual class: Point, with two integer fields and an equals method, compiles to exactly the same memory layout as struct { int x; int y; } in C. The method compiles to a free function with an extra hidden argument named this, a pointer to the object. Calling p.equals(q) compiles to Point_equals(&p, &q). No vtable, no runtime, no overhead. This is what "zero-cost" means at the smallest scale.

Add the keyword virtual to a method, however, and the compiler must arrange for it to be dispatched at runtime: the function called depends on the dynamic type of the object, not the type of the pointer the caller holds. To support this, the compiler adds one hidden field to every object of a class with virtual methods: a pointer to a per-class array of function pointers, traditionally called the vtable. Each virtual method gets a fixed slot in that array. Calling shape->area() compiles to "load the vtable pointer, index slot 0, jump to that address."

Fig 6.3 · A class, an object, and a vtable

A class with virtual functions gives each object one hidden pointer, the vptr, to a table shared by the whole class. Calling s->area() loads the vptr, reads slot 0, and jumps there: two instructions, the second an indirect call.

How it works
  1. Who sets it. The constructor writes the vptr, so a Circle always points at Circle's table, whatever type of pointer holds it.
  2. The cost. One extra load and an indirect call; when the processor predicts the target, that is close to a direct call.
  3. The C version. A struct of function pointers, kept by hand, is the same design: the Linux kernel's file_operations is one.

Inheritance is layout

Fig 6.4 · Inheritance: same vptr slot, different function

One call site, three classes: when s points at a Circle, a Square or a Triangle, the same slot 0 of each class's vtable leads to that class's own area(). The caller never changes; that is polymorphism, code written against an interface rather than an implementation.

How it works
  1. Same layout. Every class derived from Shape puts area() in the same slot of its vtable, so the call compiles to the same two instructions.
  2. New shapes for free. A Hexagon added next year works with print() unchanged and uncompiled.
  3. The rule. = 0 makes Shape::area pure virtual: Shape itself cannot be created, only its subclasses.

Encapsulation as a tool

Public, private, protected: classes can hide their state, forcing access through methods. This is enforced at compile time only. At runtime, a private field is just a field, and a determined caller can cast their way to it. Encapsulation in C++ is not a security boundary; it is a discipline the language helps you keep. Used well, it lets you change a class's internals freely, knowing the rest of the codebase cannot have grown to depend on them.

04 · RAII

The signature C++ idiom.

Stroustrup's most original contribution was not classes (Simula had those), nor operator overloading, nor templates. It was an idea that sounds obvious once stated: tie the lifetime of every resource to the lifetime of an object on the stack, and let the compiler clean up when the object goes out of scope. The acronym is RAII, Resource Acquisition Is Initialisation.

Recall from Chapter 5 that C makes you the bookkeeper. Every malloc needs a free, every fopen an fclose, every pthread_mutex_lock a pthread_mutex_unlock. Each pair must be matched on every exit path from the function, including the paths created by exceptions, which C does not have but which C++ does. The C answer is goto-cleanup style: a single label at the end of the function that frees everything in the right order, with every branch jumping to it. It works, but it does not survive refactoring.

The C++ answer is an object whose constructor acquires the resource and whose destructor releases it. Place that object on the stack. The compiler emits a destructor call wherever the object goes out of scope. Function returned normally? Destructor runs. Loop abandoned via break? Destructor runs. Function exited because an exception was thrown three frames down? Destructor runs as the stack unwinds. The bookkeeping cannot be skipped, because there is no human writing it any more.

Fig 6.5 · RAII: scope acquires, scope releases

Each resource is an object on the stack, acquired as its line runs and released by its destructor when the function exits, in reverse order. A normal return and an exception thrown by parse() unwind the same way, so no cleanup code is written and none can be forgotten.

How it works
  1. The C version. Every early return or error path must unlock, free and close by hand, usually through a shared goto label; one missed line leaks.
  2. Why reverse. Later resources may depend on earlier ones, so the compiler destroys them in the opposite order to construction.
  3. What builds on it. Containers, smart pointers and lock guards are all RAII types; it is also what makes exceptions safe to use.

Once you understand RAII, large parts of C++ become re-readable. std::vector is RAII for a heap-allocated array. std::unique_ptr is RAII for a single heap object. std::lock_guard is RAII for a mutex. std::ifstream is RAII for a file descriptor. The standard library is, to a first approximation, a catalogue of RAII wrappers around C resources, built on one principle: resources are objects, and objects clean up after themselves.

Bjarne Stroustrup
05 · The performance contract

What "zero-cost" actually means.

C++ makes one promise: you do not pay for what you do not use, and what you do use is as fast as anything you could have written by hand. The slogan is zero-cost abstraction, and it is slightly misleading. There are costs, just not at runtime: compile time, build complexity, and a generation of programmers who have to understand both layers to write C++ at all.

Consider std::sort. C's qsort takes a function pointer to a comparator, so every comparison is an indirect call through a pointer the compiler cannot see through. std::sort takes the comparator as a template argument, so the compiler generates a fresh copy of std::sort per comparator type and inlines the comparator directly into the loop. The result is a tight, branch-predictable loop with no indirect calls. Sorting a million integers on a modern CPU, std::sort typically runs about three times faster than qsort, and most of the difference is the dispatch mechanism.

Fig 6.6 · qsort vs std::sort, same algorithm, different cost

qsort reaches the comparison through a function pointer, so every comparison is a call the compiler cannot see into; std::sort is compiled for the exact comparison, which becomes two instructions in the loop. Same algorithm, a shorter path per comparison, paid for with a separate copy of the sort for each comparison type.

How it works
  1. Why C cannot inline. qsort was compiled into the C library long before your comparison function existed, so it can only call it.
  2. Templates. std::sort is compiled at your call site with the comparison's type known, so the optimiser folds it into the loop; on a million integers it typically runs about three times faster.
  3. A trap in C. The usual comparator return *(int*)a - *(int*)b; overflows for large values; (x > y) - (x < y) is safe.

The same logic runs through the entire C++ value system. Templates instead of function pointers, when you can. constexpr instead of runtime computation, when the inputs are known. Move semantics instead of copying, when the source will not be needed again. Each pushes work from runtime to compile time, where the compiler can see everything at once. C++ programmers tend to internalise this trade so completely that they forget they are making it. What a C programmer reads as luxury, a C++ programmer reads as the cost the compiler should obviously pay so the program does not have to.

06 · Modern C++

The language that ate its own complexity.

Through the 1990s and 2000s, C++ accumulated a reputation as the language with every feature, none of which were quite right. By 2010, the standard committee had reached the same conclusion. C++11, the first major standard release in thirteen years, added mechanisms that obsoleted most of the patterns the previous generation had hated: smart pointers replaced raw new/delete, move semantics replaced expensive copies, auto replaced verbose type declarations, lambdas replaced function pointers. None of the old features were removed; the new ones were so much better that competent C++ stopped using the old.

Smart pointers

A raw new in modern C++ is rare to the point of suspicion. Three class templates from <memory> handle nearly every heap allocation, each with explicit ownership semantics. std::unique_ptr owns exclusively: one owner, copying forbidden, moving transfers. std::shared_ptr owns jointly: a reference count tracks how many shared_ptrs point to the same object, and the object is deleted when the count drops to zero. std::weak_ptr observes. It does not affect the count, and accessing it requires explicitly upgrading to a shared_ptr (which may fail if the object is gone).

Fig 6.7 · Three pointer flavours, three ownership semantics

Ownership is part of the type: behind a unique_ptr the object dies with its single owner, behind a shared_ptr when its count of owners reaches zero. A weak_ptr watches without keeping its object alive, and afterwards reports that it has expired.

How it works
  1. The costs. A unique_ptr is as cheap as a raw pointer; a shared_ptr pays for an atomic count updated on every copy.
  2. Moving, not copying. A unique_ptr cannot be copied, only moved, so there is never more than one owner.
  3. Breaking cycles. Two objects holding shared_ptrs to each other never reach zero; making one link a weak_ptr lets both be freed.

Move semantics

For decades, returning a large object from a function meant copying it. C++11 added a way to move it instead: to declare "I am done with this; take it" and have the destination object steal the source's internal buffers, leaving the source in a valid-but-empty state. The mechanism is the rvalue reference, written T&&: a reference that can only bind to a temporary, signalling that the caller has no further use for the value. A class with a properly written move constructor can transfer ownership of a million-element vector in three pointer assignments.

Fig 6.8 · A move is "I'm done with this, take it"

Moving a vector copies its three pointers into the new owner and nulls the old ones; the million ints stay exactly where they are. The cost is the same for ten elements or ten million, and v1 is left empty but still valid.

How it works
  1. A copy instead. auto v2 = v1; would allocate another 4 MB and copy every int into it.
  2. std::move moves nothing. It only marks v1 as finished with, so the compiler picks the moving constructor over the copying one.
  3. Returning by value. A local vector returned from a function is moved out, or built in place, so returning large containers is cheap.
Fig 6.9 · C++ standards · the language eating its own complexity

Seven standards in twenty-five years, and the same task keeps getting shorter: an iterator loop in C++98, a range-for in C++11, a single fold with no loop in C++23. The old forms still compile, so the language keeps growing while the recommended way to write it shrinks.

How it works
  1. The two big ones. C++11 (auto, lambdas, move semantics, smart pointers) and C++20 (concepts, modules, ranges, coroutines) each changed what "modern C++" means.
  2. The books. Scott Meyers wrote Effective Modern C++ (2014) because C++11 had overtaken much of his Effective C++.
  3. Little is removed. auto_ptr, gone in C++17, is a rare exception; that is why the language only grows.

The seam to Chapter 7

C and C++ are both languages that face the machine. They give the programmer enormous power (direct memory access, deterministic destruction, zero-cost abstraction) and demand in return careful attention to what the machine actually does. By the late 1980s these languages ran every system that mattered, and many programmers took this as the trade every language must make. In 1989, over a Christmas holiday in Amsterdam, Guido van Rossum asked the opposite question. What if a language did not face the machine at all?

"Within C++, there is a much smaller and cleaner language struggling to get out."

Bjarne Stroustrup, The Design and Evolution of C++, 1994

Where C++ still bleeds. Smart pointers and RAII closed most of the manual-memory wounds, but three classes survive. Use-after-move: a moved-from object is in a valid but unspecified state, and reading it yields an answer that means nothing. That is legal, silent, and wrong. Vtable corruption: a use-after-free on a polymorphic object lets an attacker overwrite the vtable pointer and route every virtual call to attacker-chosen code, the modern descendant of the buffer overflow from Chapter 3. Iterator invalidation: the moment a vector reallocates, every outstanding iterator is a dangling pointer. The continuing CVE rate in C++ codebases is what motivates the slow migration to Rust in security-critical paths.

01 · Compiled vs interpreted

Two pipelines, two trades.

The first Lisp interpreter ran on an IBM 704 at MIT in 1959. John McCarthy had written a paper proposing a new language defined recursively in terms of itself (its core function, eval, evaluated Lisp expressions in Lisp) but had not implemented it. A research assistant named Steve Russell, who had been transcribing the paper, realised that eval looked like working code rather than mathematical theory, and spent a few weeks turning it into machine code by hand. The result was the first interpreter that mattered: a program that read each Lisp expression at runtime and executed it directly, without ever producing a separate binary. The BASIC of the first microcomputers, a decade and a half later, arrived the same way: an interpreter squeezed into ROM, translating each line as it ran. The argument over when a program should be translated to machine instructions is older than C and older than UNIX. Once, on the developer's machine, into a self-sufficient binary? Or every time it runs, in flight, on the user's? C took one side. Python took the other. The first gives you speed. The second gives you back something C never thought worth bargaining for: your time.

A compiled language passes through a long pipeline before it ever runs. A C source file becomes preprocessor output, becomes parser tokens, becomes an abstract syntax tree, becomes intermediate representation (often LLVM IR), becomes optimised IR, becomes target-specific assembly, becomes machine code in an object file, becomes a linked executable. All of this happens in advance, on the developer's machine. When a user runs the program, the CPU loads the instructions and executes them; nothing translates at runtime. Speed is bounded only by the hardware and the compiler's cleverness.

An interpreted language does most of the same pipeline, but at runtime, on the end-user's machine. Python source becomes tokens, becomes an AST, becomes bytecode: a sequence of small, simple opcodes for a virtual machine. The translation is cached between runs; the interpretation itself is paid for every time. The CPython interpreter is a giant switch statement in C that reads each opcode and performs its action. The CPU executes the interpreter; the interpreter executes your code. Every Python statement becomes hundreds of CPU instructions in the interpreter's dispatch loop, plus the actual work.

Fig 7.1 · The two pipelines, side by side

C pays for translation once, on the developer's machine, and every run executes native code; Python translates on the user's machine, caches the bytecode in a .pyc file, and interprets it on every run. Python ships source that runs wherever there is an interpreter, and pays in cycles each time it runs.

How it works
  1. C. The compiler parses, optimises and emits machine code; the linker joins the pieces into one executable for one kind of machine.
  2. Python. CPython parses to a syntax tree, compiles it to bytecode, saves that in __pycache__, and its eval loop runs one bytecode instruction at a time.
  3. In between. Just-in-time compilers (PyPy, and CPython 3.13's experimental JIT) turn hot bytecode into machine code while the program runs.
02 · Van Rossum 1989–91

A Christmas hobby that ate the world.

Christmas 1989, at the Centrum Wiskunde & Informatica in Amsterdam, Guido van Rossum was bored. He had spent three years on a research language called ABC, which had failed to gain traction outside CWI. Over the holiday break, working from home, he started writing an interpreter for a new language that borrowed ABC's clarity and added the things ABC had refused: modules, exceptions, escape hatches into C. He named it after a British comedy troupe he liked. By 1991 he had released it to USENET, where it began the slow, improbable march that ended with it eating data science, scientific computing, and most of the world's introductory programming courses.

Python's design choices trace to instincts that Tim Peters wrote down in 1999 as the Zen of Python. Readability counts: indentation is part of the grammar, so badly indented Python is also syntactically wrong, which enforces consistent layout across every codebase. Explicit is better than implicit: no hidden conversions, self spelled out as the first parameter of every method. There should be one-- and preferably only one --obvious way to do it: the anti-Perl principle, deliberately the opposite of "many ways to skin a cat." These were aesthetic commitments before they were technical ones.

Fig 7.2 · Python's slow conquest

From a project van Rossum began over Christmas 1989 to the everyday language of data science. The defining event is the split: Python 3 broke compatibility in 2008, and Python 2 lived beside it for twelve years before it was retired in 2020.

How it works
  1. The name. van Rossum (1996): "I chose Python as a working title for the project, being in a slightly irreverent mood (and a big fan of Monty Python's Flying Circus)."
  2. What 3.0 fixed. Text became Unicode, 1/2 became 0.5, and print became a function: each one broke old code.
  3. The inheritance. From ABC, Python took indentation as structure and a taste for being easy to read.
03 · Dynamic typing

Types are properties of values, not variables.

In C and C++, a variable has a type, declared once and fixed forever. In Python, a variable is just a name that can refer to any value, and a value carries its own type. Write x = 5, then x = "hello", then x = [1, 2, 3]. All legal. The interpreter checks types at every operation, paying for that check in cycles. The programmer is paid back in fewer declarations and fewer mistakes about them.

Statically typed languages (C, C++, Rust, Go, Java) check types once, at compile time. Hand a string to a function that wants an integer and the compiler refuses; the program never runs at all. Dynamically typed languages (Python, JavaScript, Ruby) check types at runtime. The same mistake compiles fine, runs fine until it doesn't, and dies with a TypeError at the offending statement. The static side is safer; the dynamic side is more fluid. Reasonable people have disagreed about which trade is correct for thirty years.

Python pushes the dynamic side to its logical limit with duck typing: "If it walks like a duck and quacks like a duck, it is a duck." Translation: an object is acceptable wherever its methods are acceptable, regardless of its declared class. A function that calls obj.read() works on any object that has a read() method (a file, a network socket, a mock for testing), with no shared base class required. The price is that "acceptable" is checked at runtime; the benefit is that you can compose objects in ways the original designers never anticipated.

Fig 7.3 · Duck typing: behaviour, not lineage

announce works on any object that has a speak method: Python looks the name up on the object itself, at the moment of the call. A Duck and an unrelated Robot both answer; an int has no speak, and the mistake surfaces only when that call runs, as AttributeError.

How it works
  1. The strength. Any object with the right method fits, including ones from libraries written after the function was.
  2. The weakness. The contract "must have speak()" is checked by running the code, not by a compiler beforehand.
  3. The middle way. Type hints with typing.Protocol let a checker such as mypy verify the contract before the program runs, without any shared parent class.
04 · The GIL and concurrency

One Python thread runs at a time. There are reasons. They are running out.

Python's threads are real OS threads. But CPython, the reference interpreter, contains a single global lock, the GIL (Global Interpreter Lock), that ensures only one thread holds the right to execute Python bytecode at any moment. On an eight-core CPU running a multithreaded Python program, seven cores sit idle. This sounds like a bug. It is the consequence of a deliberate design decision from 1992, whose bill came due only when the cores multiplied.

The reason is reference counting. Every Python object carries a count of how many names point to it; when the count drops to zero, the object is freed. Updating the count must be atomic, and here is what happens if it is not: two threads decrement at once, both read 2 and both write 1, and one decrement is simply lost. An object that should be dead now lives forever. Lose an increment instead and the count hits zero early: the object is freed while a thread still holds it, and Chapter 5's use-after-free arrives in a language that promised you would never see one. The GIL is the simplest possible solution: serialise everything Python-level, so refcounts cannot race. Removing the GIL has been attempted many times, and the obstacle is practical: fine-grained locking slows down single-threaded code, which is most code, by 30–50%. PEP 703, accepted in 2023, lays out a way to remove the GIL while keeping single-threaded performance acceptable, and Python 3.13 ships an opt-in no-GIL mode. Default-on no-GIL is targeted for the late 2020s.

Fig 7.4 · Two Python threads, one GIL

With the GIL, two CPU-bound threads take turns, the lock passing between them every 5 ms, so only one runs at a time; a thread waiting on I/O releases it, and then the other gets real work done. Python 3.13's optional free-threaded build removes the lock, and both threads run at once.

How it works
  1. Why one lock. CPython's reference counts and internal structures were never safe to update from two threads at once; a single lock made them safe and kept the interpreter simple.
  2. The interval. sys.getswitchinterval() is 0.005 seconds by default: after that, the running thread is asked to hand the lock over.
  3. Removing it. PEP 703's free-threaded build uses per-object locks and biased reference counting; in 3.13 it is optional, and single-threaded code runs somewhat slower in it.
Fig 7.5 · asyncio: cooperative scheduling on one thread

One thread runs an event loop: each task runs until it awaits a network reply, and the loop switches to another that is ready, so the waits overlap although only one task runs at a time. No locks are needed, because a task can be interrupted only where it says await.

How it works
  1. The history. asyncio arrived in Python 3.4 (2014); the async def and await keywords followed in 3.5.
  2. The idle gap. When every task is waiting, the loop asks the operating system (epoll, kqueue) which sockets are ready, so one thread can watch thousands of connections.
  3. The catch. A task that computes without awaiting holds up every other task, and async spreads to every function that calls an async one.
05 · How Python is built

CPython is one million lines of C running your script.

"Python" is a language specification. CPython is the reference implementation: the interpreter you almost certainly used the last time you typed python at a shell. It is roughly one million lines of C, maintained since 1991 by Guido van Rossum and now a global team of core developers.

The pipeline inside CPython is short and unromantic. The tokeniser splits the source file into tokens: identifiers, numbers, operators, indents and dedents. The parser assembles tokens into an abstract syntax tree. The compiler walks the AST and emits a list of bytecode instructions for a stack-based virtual machine. The evaluator (the famous ceval.c, ten thousand lines long) is a giant switch statement that reads each bytecode and dispatches it to the C handler that carries it out. Bytecode is cached on disk in __pycache__/ as .pyc files, so later imports skip the first three steps unless the source has changed; the script you invoke directly is recompiled each run.

Fig 7.6 · CPython's pipeline, in detail

CPython turns a + b * c into bytecode for a stack machine: three loads push 2, 3 and 4; BINARY_OP * pops 3 and 4 and pushes 12; BINARY_OP + pops 2 and 12 and pushes 14. The eval loop does exactly this, one instruction at a time, for every line of Python.

How it works
  1. See it yourself. import dis; dis.dis("a + b * c") prints this bytecode.
  2. Since 3.11. One BINARY_OP with an argument replaced BINARY_ADD, BINARY_MULTIPLY and the rest, and the interpreter specialises hot instructions once it has seen their types, such as BINARY_OP_ADD_INT.
  3. The loop. ceval.c jumps from each instruction to its C handler, using computed gotos where the compiler supports them.
Fig 7.7 · Why Python is slow (and why nobody minds)

A single integer addition in C compiles to a single CPU instruction. The same operation in CPython performs roughly 150 instructions of work: unbox both operands from their PyObject boxes, check that they are both ints (and not, say, a custom class with __add__ overridden), dispatch to long_add, allocate a new PyObject for the result, bump its refcount, push it onto the eval stack, decrement the refcounts of the operands. CPython is slow because it does, at runtime, the work the C compiler does once at compile time. PyPy, an alternative Python implementation with a tracing JIT, recovers most of the gap for hot loops. CPython remains the reference implementation, slow and stable. For most workloads, this gap is invisible because the bottleneck is elsewhere (disk, network, the database, the model on the GPU) and Python is not the thing being measured.

06 · Why Python won data science

The two-language strategy.

Python is slow. Numerical work is the most cycle-hungry thing computers do. By every naive analysis, Python should not be the language of numerical computing, scientific simulation, or machine learning. It is, anyway, thanks to one design pattern, now the unspoken contract of the whole ecosystem: write the human-facing code in Python, write the performance-critical code in C or Fortran, and bridge them with a thin wrapper.

Fig 7.8 · How NumPy actually does work

A single NumPy call descends through three layers and ends in hand-tuned numerical kernels that have been refined by specialists since the 1970s. The Python programmer never touches Fortran; the BLAS authors never touch Python. The wrapper layer in NumPy is what makes the bridge work: it accepts Python objects, validates types and shapes, calls the right BLAS routine, and returns a Python object pointing into the result buffer. The runtime cost of the Python layer is amortised across the giant compute the BLAS layer performs. For a 1000×1000 matmul, Python's overhead is microseconds; BLAS's compute is milliseconds. The Python layer is invisible.

Fig 7.9 · The same matmul, two ways

A 1000 × 1000 matrix multiplication in pure Python takes about two minutes: three nested loops, a billion multiply-adds, each paying the interpreter tax. The same multiplication in NumPy takes a hundredth of a second. Four orders of magnitude. The difference is not Python improving; the difference is that np.dot never executes Python in its inner loop. Once the BLAS call returns, you are back in Python, plotting or printing or storing, work where the human's time matters more than the CPU's. This is the deal: humans use Python. The machine uses C and Fortran. They meet at the wrapper.

The verdict

Python beat every "fast" language for data science not because it won a benchmark (it lost every benchmark) but because the people doing the work were not benchmark writers. They were physicists, biologists, traders, machine-learning researchers. They had problems to solve, not loops to tune, and Python let them think about the problem instead of the language. The two-language strategy delegated the parts where cycles mattered to people whose career was making cycles cheap.

This is, almost exactly, the trade C and C++ refused to make. Stroustrup believed any abstraction must be free; Ritchie believed any abstraction must be simple. Van Rossum believed the cost of an abstraction was paid in human attention, and he was willing to spend a hundred machine cycles to save a programmer five minutes of typing. Three languages, three positions on the same axis.

The sharpest edge is one line long. pickle.loads(data) looks like a parser and is an interpreter: a pickle is a small program for a stack machine, and the machine can construct any Python object, including one whose construction calls os.system(). Python's other edges are the same property (data becoming code with almost no friction) met at different doors: eval() and exec() on user input repeat the same data-as-code mistake that gives Chapter 13's SQL injection its name, and a PyPI package named request, one keystroke from requests, runs whatever it likes the moment someone installs it.
